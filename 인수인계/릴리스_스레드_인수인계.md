## 3. 릴리스 절차 (그대로 따를 것)
1. 받은 브랜치를 합친다. 충돌은 양쪽 의도를 읽고 손으로 푼다.
   - force push는 막혀 있다. 필요하면 `git merge -s ours origin/<브랜치>` 뒤 일반 push.
2. `GOEI_VS=1 npm run release:prep` (판을 올릴 때만 `-- --bump patch`)
   - 빌드, 카드, 단위 시험(648개)을 돈다.
   - 판을 올리면 옛 `.scratch/fixture`를 옆으로 치운다.
3. `dist/vs`를 `release/vs`로 복사한다.
4. `git status`로 release/에서 **지워진 파일이 없는지** 확인한다.
5. 브라우저 시험은 **바꾼 곳에 닿는 것만** 돌린다. 전체 시험은 미리 말하고 허락받는다.
   - 명령: `npm run test:browser -- --only a,b --no-build`
   - qc-loader와 install은 늘 돌린다. qc-loader는 prep 뒤에만 통과한다(release/icon.webp가 필요하다).
6. 커밋·push → PR(머리 템플릿 없음) → squash 합치기.
7. **release.yml이 push로 저절로 안 뜬다.** 11-07과 11-09 두 번 다 안 떴다.
   - 손으로 돌린다: GitHub Actions에서 release.yml, workflow_dispatch, ref main.
   - 릴리스는 prerelease라서 list_releases로 확인한다.
8. 사용자에게 링크로 보고한다.

**릴리스 승인**: 「릴리스해」 또는 그에 준하는 사용자 지시가 있을 때만 main에 합친다. 11-09에는 「받은 것 합치고 → 전수점검 → 고치고 → 최종 릴리스」 순서 지시가 곧 승인이었다.
