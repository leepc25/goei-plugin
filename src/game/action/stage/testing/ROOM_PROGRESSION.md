- 출동 시드 **270**, 깊이 **4**, 퍼즐 방 **(1,2)**, 계획 `room:4:1,2:34`,
  셔터 **x=610**, 플레이어 **x≈357.33**: `스위치 1,3,2 n=3`.
- 봇의 목표 조회 `inTheWay()`가 입력 전 순서 카운터를 올렸다. 같은 프레임에
  `go(pr.x)`를 두 번 호출하면 실제 E는 한 번인데 카운터는 두 번 진행했다.
- 대역 엔진이 실제 전달한 상호작용만 기록한다. 목표 조회는 순서를 바꾸지 않고,
  오답이면 입력 이력을 통해 처음부터 다시 푼다. 주민·밥상·표지도 실제 입력을
  기준으로 추적한다. 가까운 다른 소품에 E가 잡히면 목표까지 더 정확히 걷는다.
- 정답 판정 자체는 정상이다. 오답 → 1 → 3 → 2에서 닫힘 상태가
  `[true, true, true, false]`이며, 재방문 상태 보존과 뒤편 손잡이도 검사했다.
  체력 보정·시간 한도·필수 정리·열쇠·잠금·보상 기준은 낮추지 않았다.

## 통합 담당에게 필요한 패치

`module-progression.patch`는 **제안만 저장했으며 module.ts에 적용하지 않았다**.

1. **17 / 깊이 4 / chase / 도착 방 (2,0)**: 방을 통과한 뒤에도 추격이 계속되어
   계단 **x=1864**로 돌아가려는 요원을 **x≈1959**까지 밀어낸다. 현재 보행 시험의
   `17:chase:4`에서 재현된다. `24:chase:4`도 동일 계열이다.
2. 오른쪽 절반의 계단으로 들어오는 경우도 추격은 왼쪽에서 시작한다. 아직 통과
   거리를 채우지 못한 상태에서 왼쪽으로 돌아가야 하면 벽과 계속 충돌한다.
   **17 / 깊이 4 / chase / (3,1)**, 위 계단 **x=1232** → 진입 **x=1302**.
   깊이 5의 하역장에서도 발생하며 `17:replica:4`, `17:dark:4`,
   `17:silent:4`, `17:puzzle:4`는 해당 다음 층에서 멈춘다.

최소 수정안은 오른쪽 절반 진입을 기존 오른쪽 문 진입처럼 처리하고,
방 통과 목표를 달성하면 추격 위치와 표시를 비활성화하는 두 지점이다.
필수 정리 판정이나 시험 assertion은 바꾸지 않는다.

통합 시:

```sh
git apply --check src/game/action/stage/testing/module-progression.patch
git apply src/game/action/stage/testing/module-progression.patch
npm run typecheck
npm run build
node --test tests/stage.test.mjs
```

검증 때는 esbuild `onLoad`로 이 두 변경만 메모리에 적용하여 동일 시험을 실행했다.
작업 트리의 통합 담당 파일은 그대로다. **제안 적용 시 스테이지 40/40 통과**:
기존 L1 시작 10개 시드와 8개 유형 × 2개 시드(17,24)의 26개 출동 모두
필수 방 정리 → 다음 층 → 정비 구역 → 다락방 로프 귀환.
열쇠 72개, 잠금 72개, 보상 102개, 강화 244개, 방문 방 937개를 확인했다.
