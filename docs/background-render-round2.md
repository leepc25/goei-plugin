# 배경 렌더 2차 검증 · 2026-10-22

브랜치: `codex/background-render-round2`. 기준: `0d43a4496bff1cdc7c0122e273a43475c9134356`.
`origin/codex/metroidvania-run-system`을 명시적으로 fetch한 뒤 독립 worktree에서 작업했다. 기존 checkout은 변경하지 않았다.

## 재현과 변경

- 실제 Chromium에서 소품을 자산 팩 주입 전에 조회하고, PNG를 뒤늦게 주입했다. 기준판은 `drawPropArt()`가 계속 false, `propArtSize()`가 계속 null이었다. 없는 자산을 null로 영구 보관하던 두 캐시를 수정했다. 로딩 중인 이미지는 한 객체를 공유하고 로딩 완료 뒤 그린다.
- `createPattern()`의 첫 반환값을 null로 지연시켰다. 기준판은 다음 호출도 null이었다. 성공한 패턴만 저장하여 다음 프레임에 재시도한다. 이미지와 패턴이 준비되기 전에 빈 화면을 합성해 보관하는 캐시는 도입하지 않았다.
- 같은 자산 경로의 source가 바뀌면 이미지·PNG 크기와 파생 패턴·색조·벽 끝 색을 갱신한다. 교체된 이미지가 준비되기 전에는 이전 그림을 내보내지 않는다.
- 실제 배경 PNG와 생산 코드로 긴 벽, 배관, 낮은 소품 줄, 책상 두 개 묶음, 높은 표지를 그렸다. 카메라 밖 이미지 호출을 확인한 뒤 캔버스의 현재 변환과 그림의 실제 크기로 생략한다. 그림이 화면 밖인 경우에도 처리 완료를 반환하여 대체 그림을 요청하지 않는다. 명패 돌출과 그림자·소수 좌표 경계에는 여유를 둔다.
- 벽 위·아래와 바닥 명암의 반복 그라데이션 생성은 context별 최대 32개 캐시로 대체했다. 가로 이동은 수직 명암을 재사용하고, 확대·세로 이동·기울기·높이 변경은 별도 항목을 사용한다. context는 WeakMap으로 보관한다.

런타임 수정은 `src/game/action/art/bg.ts` 하나다. 원본 PNG, 캐릭터, stage 배치와 통합 담당 소유 파일은 변경하지 않았다.

## 전후 측정

Chromium headless, 논리 캔버스 1280×720. 기준 소스는 테스트가 `git show 0d43a449:src/game/action/art/bg.ts`로 읽어 현재 소스와 같은 페이지에서 별도 번들로 실행한다. 각 장면 로딩 완료 뒤 100회씩 5묶음 호출의 중앙값이다. 아래는 카메라 x=0 결과. 시간은 JS 호출 제출 시간이며 GPU 완료 시간이나 게임 전체 FPS가 아니다.

6장면 × 5변환(원점, 소수 카메라 이동, 축소·세로 이동, 좌우 반전, 기울기) **30쌍 모두 RGBA 바이트 차이 0**. 워밍업 후 500회 호출 동안 새 Image 생성은 기준·수정 모두 0. 이 범위에서 반복 이미지 생성/디코딩 요청 문제는 찾지 못했다. 브라우저 내부 GPU 텍스처 재업로드·메모리 압박 시 디코딩은 별도로 계측하지 않았다.

실제 게임은 새로 시작 → 컷씬 건너뛰기 → 첫 사무실의 가구를 돌아 키보드로 문까지 이동 → E → 2층 복도, 이후 `deploy(seed=4242)`로 탐사방을 열고 이동했다. 본부 문 통과에 위치 주입/goto는 사용하지 않았다. 탐사 진입은 임무 대화 완주 대신 엔진 deploy API를 사용했다.

| 실제 게임 배경 | 기준 | 수정 |
| --- | --- | --- |
| 첫 사무실 | fillRect 35, gradient 1, drawImage 0 | 동일 |
| 2층 복도 | fillRect 35, gradient 1, drawImage 0 | 동일 |
| 탐사 `room:1:0,0:1` | gradient 10/회 | 4.015/회 (새 측정 context의 첫 3개 생성 포함, 이후 4/회) |

실제 배경 200회 평균 호출 시간은 사무실 0.0155→0.0140ms, 복도 0.0205→0.0160ms, 탐사 0.0465→0.0400ms였다. 서로 다른 실행 시점의 작은 수치여서 유의한 FPS 개선 근거로 삼지 않는다. 특히 사무실·복도는 `hub.ts`의 코드 그림을 사용하며 수정하지 않았으므로 속도 개선을 주장하지 않는다. 발견한 반복 그리기 비용과 재현 가능한 호출 수 감소가 성능 근거다.

- 타입 검사·빌드 성공, 전체 테스트 파일 39개 통과.
- 새 `tests/background-render-round2.test.mjs`: 늦은 팩 주입, 로딩 중 이미지 객체 중복 방지, source 교체와 크기/패턴 갱신, 화면 밖 처리 반환값, null 패턴 재시도.
- 기존 본부 벽 배치·문 통과·스테이지 회귀 포함 전체 통과.
- 새 Chromium 스크립트: 위 30쌍 픽셀 비교, 성능 카운터, 실제 로딩 후 복구, 실제 첫 문 이동, 탐사방 그리기와 이동. pageerror 0.
- `PLAYWRIGHT_MODULE`과 `CHROMIUM_PATH`로 설치 위치 변경 가능. 기본 경로는 이 클라우드의 Playwright와 `/usr/bin/chromium`이다. 로컬 HTTP만 사용한다.
- 출력: `out/background-render-round2/result.json`, `office.png`, `corridor.png`, `exploration.png`. 최초 수정 전 실측은 같은 폴더 `baseline.json`에 남겼다. `BASELINE=1`은 실패 단언을 생략하는 재현용 모드이고, 최종 검증은 옵션 없이 실행했다.
- `npm run build`가 생성한 `dist/goei-action-game.html`을 `out/background-render-round2/goei-background-round2.html`로 별도 복사했다. 배경 코드가 반영된 기술 검수용 플레이 HTML이며 캐릭터 그림을 새로 제작/승인한 결과가 아니다. 생성 HTML과 스크린샷은 커밋하지 않는다.

## 통합과 남은 범위

공용 연결 패치는 필요 없다. 기존 공개 함수 시그니처를 유지하므로 이 브랜치의 `bg.ts` 변경으로 호출부에 적용된다. 통합 담당은 이 브랜치를 검토해 반영하면 된다. 다른 작업 브랜치 병합, main/공용 브랜치 push, 플러그인 릴리스는 하지 않았다.

실기기 모바일/Safari, 모든 깊이 수동 완주, 장시간 메모리 압박과 GPU 완료 시간은 미검증이다. 첫 사무실·복도의 정적 그림 전체를 캐시하는 작업은 이번 측정에서 필요성이 확인되지 않아 공용 hub.ts 패치를 만들지 않았다. 이미지 네트워크 자체가 실패한 경우 같은 URL을 무한 재시도하는 정책도 추가하지 않았다.
