# 리수폿 v2.0.2 기능 전수 검토와 이식 설계 (2026-10-26)

> **2026-10-26: 이 문서는 `리수폿_대비_전체정리.md`(기능 전수·비용·효과)와 `인물기록_호감_통합설계_3판.md`(세부 설계)로 대체됐다.** 인물 위키를 「안 옮김」으로 판정한 부분이 틀렸다(로어북은 갱신되지 않는 죽은 정보). 기능 목록 표는 그대로 유효하다.

## 0. 결론 먼저

| 판정 | 기능 |
| --- | --- |
| **그대로 옮김** | 호감 점수 체계(범위·초기값 표·변화량 표·8단계와 단계별 행동 설명), 계산 엔진 규칙(정해진 값만, 턴 상한, 예외값, 배율, 중복 방지, 고정, 이유 필수 직접 수정), 근거 인용 검증, 잘못된 항목만 버리기, 다시 굴리기 되감기 규칙, 「이름표만으로 높이지 않기」 같은 판단 지침 |
| **바꿔서 옮김** | Writer(응답 뒤 기록) → **관계 읽기** 1회 호출 / Director(연출 메모) → **코드 템플릿 주입**(모델 호출 0) / 관계·호칭 → 유저 대상 호칭만 / 감정 표현 기준 → 인물별 표현 정도 / NEW 표시·진행 표시·변경 전후 보기 → 관계 화면에 작게 / 추가 프롬프트 → 관계 읽기에만 |
| **나중에 검토** | 인물끼리 관계(NPC 감정), 취향(첫인상) 축, 말투 변화 조짐 세기, 관찰자 모드 |
| **안 옮김** | Router·위키 검색·Hypa 기억, 인물 위키 전체, 지각, 불륜 의심, 음란도, 서사 리듬, 자체 모델 연결·키 관리·PDF, 실행 기록 재생, 봇별 기능 세트, 고정 키워드·추적 ID, 폴더·합치기, 백업 |

**한 줄 요약**: 리수폿의 매 턴 3회 호출(Router → Director → Writer) 가운데 **Writer만 가볍게 옮기고, Director는 코드가 대신**한다. 호감 숫자 체계와 판정 지침은 리수폿 것을 그대로 쓴다. 결과적으로 **매 턴 1회 호출**(또는 몇 턴에 1회)로 본편과 필드가 같은 호감을 쓴다.

## 1. 리수폿 전체 구조

### 1-1. 한 턴의 흐름 (진행 표시 단계 `ROUTER → DIRECTOR → MAIN → WRITE → SAVE`)

```
유저 입력
 ├ ① Router (보조 모델): 위키 목록(제목·별명·태그만)+최근 대화 → 이번 응답에 필요한 인물·장소 문서 고르기, 처음 나온 이름 알림
 ├ ② Director (보조 모델): 고른 문서 본문·수치·최근 대화 → 연출 메모(영어) 작성. 자료가 모자라면 chat/wiki/lore 검색 요청 1회
 │     · 「판단형」: 반응 방향·말투·드러내면 안 되는 정보까지
 │     · 「사실 전달형」(director_facts): 사실·누가 무엇을 아는지만, 연출 제안 금지
 ├ ③ Main (본편 모델): 연출 메모가 끼워진 요청으로 평소처럼 응답
 └ ④ Writer (보조 모델): 본편 응답을 읽고 인물 위키에 JSON 제안(새 인물·사실·말투·감정·수치 연산) → JS가 검증·계산·저장
```

### 1-2. 화면 (탭 5개)

| 탭 | 내용 |
| --- | --- |
| 흐름 | 턴마다 켜고 끄는 공통 설정, 단계별 모델·예산, 고정 키워드, 관계 기록 |
| 인물 | 인물 위키(사람별 문서, 첫인상·현재 평가 카드, 수치 카드, 고정, 폴더, 합치기, 추적, AI로 채우기) |
| 기능 | 호감·취향, 관계·호칭, 지각, 의심, 음란도, 서사 리듬 켜기·끄기와 배율, 봇별 세트 |
| 프롬프트 | 내장 프롬프트 수정, 사용자 추가 프롬프트(단계·범위 선택) |
| 관리 | 실행 기록·재생, 토큰 사용량, 백업·복원, 기록 보관 수, 진단 |

### 1-3. 저장

- 플러그인 저장소(RisuAI 세이브에 포함). 채팅·봇 단위 키. 실행 기록 상한 200만 자.
- 다시 굴리기 판정: **「같은 자리에 새 chatId」면 다시 굴리기로 보고 이전 응답의 기록을 되감는다**(`auto-wiki.mjs` V29). 리수폿이 실제 Risu에서 쓰는 규칙이라, 우리 설계 2판에서 「미검증」으로 둔 chatId 동작의 유력한 근거다(그래도 우리 쪽 실측 1회는 한다).

## 2. 기능 전수 표

판정: ● 그대로 옮김 · ◐ 바꿔서 옮김 · ○ 나중에 검토 · ✕ 안 옮김

### A. 실행 흐름

| 기능 (모듈) | 리수폿에서 하는 일 | 판정 | 이유 | 우리 쪽 |
| --- | --- | :---: | --- | --- |
| Router (`router-runtime`, `router-fixed`) | 매 턴 필요한 위키 문서 고르기 | ✕ | 우리 플러그인이 이미 로어북 고르기(`core/lore.ts`, `storeLore`)로 같은 일을 한다. 둘이면 충돌·비용 | 관계 주입 대상 인물은 코드가 이름 찾기로 고른다(3-2) |
| Director 판단형 (`director-runtime`) | 연출 메모를 모델로 작성 | ◐ | 매 턴 호출 비용이 크고, 우리에게 필요한 건 「관계에 따른 태도」뿐 | **코드 템플릿**: 단계별 행동 설명 문장(리수폿 `metricStageDescription`과 같은 방식)을 본편 요청에 끼움 |

| 단계별 대화 예산 (`stage-context`) | 단계마다 최근 대화 몇 턴 넣을지 | ◐ | 관계 읽기 한 단계만 있음 | 「관계 읽기에 넣을 직전 턴 수」 설정 하나 |
| 본편 훅 (`main-wiki-hook`, `runtime-hooks`) | 본편 요청에 메모 끼우기, 재시도 캐시 | ◐ | 우리 `beforeRequest`에 이미 끼우는 자리가 있음 | `onBeforeRequest`의 상태창 블록 뒤에 관계 블록 |

| 진행 표시 (`mission-progress`) | 단계별 진행 패널 | ◐ | 단계가 하나뿐 | 관계 화면·게임 구석에 「관계 갱신 중」 |
| Hypa 기억 참조 (`hypa-reference`) | Risu 장기 기억을 Director에 | ✕ | Director가 없음 | — |
| 사건 시간순 정렬 (`event-chronology`) | 사건 문서 시간순 | ✕ | 사건 문서가 없음 | 장부는 채팅 순서로 계산 |

### B. 인물 위키 (People)

| 기능 | 하는 일 | 판정 | 이유 | 우리 쪽 |
| --- | --- | :---: | --- | --- |
| 인물 문서 칸 13종 (`core.identity`~`core.event_summary`) | 기본정보·성격·현재상태·인간관계·말투·행동경향·아는 정보·목표·행적·현재장면·요약 | ✕ | 본편 모델이 읽는 인물 정보는 **캐릭터 로어북(요원 시트)**이고 우리 로어북 고르기가 넣는다. 괴담위키(`WIKI｜` 항목)는 비활성이라 컨텍스트에 안 들어가는 화면용 읽을거리다. 리수폿 인물 위키를 또 끼우면 로어북과 겹치고 매 턴 비용이 든다. 다만 「이 채팅에서 그 인물에게 일어난 일(현재 상태·행적·아는 정보)」은 로어북에 없는 정보라, 필요하면 별도 기능으로 검토 | 관계만 장부로 |
| 새 인물 자동 생성 (`writer-new-characters`) | 처음 나온 이름으로 문서 생성 | ○ | 위키 밖 인물(사용자가 만든 NPC) 관계를 쌓을 때 필요 | 1단계는 명단 밖 이름 무시. 이후 「새 인물 관계만 생성」 |
| 별명 (`aliases_add`, `people-source-match`) | 다른 이름 표기 모으기, 띄어쓰기·하이픈 차이까지 맞춤 | ◐ | 「부장」, 「쟈알디 부장님」 찾기에 필요 | 위키·폰 연락처·대사 JSON에서 별명 표를 미리 생성. 맞춤 규칙(문장부호 정규화, 조사 「에」 처리)은 리수폿 것 참고 |
| 정체 확인 (`contextual-identity`, `identity-links`) | 비슷한 이름이 같은 사람인지 근거로 검토 | ✕ | 명단이 고정(52명) | — |
| 합치기 (`person-merge`) | 두 인물 문서 합치기 | ✕ | 같은 이유 | — |
| 고정 핀 (`people-pins`) | 칸·수치 고정, 자동 변경 무시 | ● | 사용자가 정한 관계를 지킬 수단 | 관계 화면 📌(manual pin 사건) |
| 폴더·정렬 (`people-folders`) | 인물 목록 폴더 | ✕ | 명단이 작고 고정 | 소속별 묶음 표시로 충분 |
| 추적 ID·고정 키워드 (`auto-tracking`, `router-fixed`) | 기록 대상 인물 제한 | ✕ | 명단이 고정 | 「관계 읽기 대상」 = 위키 인물 전원 |
| 로어북에서 가져오기 (`people-import`, `people-lore-selector`, `cbs-*`, `source-seed`) | 로어북을 읽어 인물 문서 초기화, CBS 변수 처리 | ◐ | 초기값을 정할 때만 필요하고, 우리는 개발 때 미리 만들 수 있음 | 개발 때 Claude가 위키로 `relations-base.json`을 만들고 사용자 검수(실행 중 비용 0) |
| 필수 개요·미확인 (`character-overview`, `overview-owner`) | 모르면 「미확인」 | ✕ | 인물 문서가 없음 | — |

| 다시 채우기·꼼꼼히 다시 채우기 (`person-refresh`, `person-thorough-refresh`) | 인물 문서를 모델로 다시 작성 | ◐ | 관계를 처음부터 다시 읽고 싶을 때 | 「최근 N턴 다시 읽기」 버튼(옛 채팅 소급과 같은 기능) |
| 수동 교정 (`people-command`) | 사용자가 말로 고치라고 지시 → 변경 전후 확인 | ◐ | 관계 고치기에 유용 | 관계 화면 직접 수정(단계 선택+이유). 말로 지시하는 AI 교정은 안 함 |
| 칸별 AI 채우기 (`people-field`, `people-metric-ai`) | 빈 칸을 AI로 채우기, 수치 검토 | ✕ | 칸이 없음 | — |
| NEW 표시 (`new-markers`) | 이번 턴에 바뀐 곳 표시 | ◐ | 관계 변화를 바로 보이게 | 관계 화면·게임 이름표 옆 ↑↓, 최근 변화 강조 |

### C. 기능 (features)

| --- | --- | :---: | --- | --- |

| **관계·호칭** `register.*`, `core.speech` | 대상별 호칭·존댓말을 느리게 바뀌는 기록으로. 명시적 허락이나 두 장면 이상 일관되면 바꿈 | ◐ | 잼트리 「후배」처럼 호칭이 핵심. 이야기 속에서 반말 허락 등이 생기면 필드 대사와 본편이 따라가야 함 | 3-4. 유저 대상 호칭만 |
| 말투 다양성 1단계 (`speech-variety` one) | 대상별 말버릇 기록 | ✕ | 대사 JSON·카드가 말투를 이미 정함 | — |
| 말투 변화 조짐 세기 (`speech-variety` two) | 같은 방향 조짐 3번이면 호칭 변경(묻기/자동) | ○ | 호칭 변경의 오판을 줄이는 좋은 장치 | 3-4의 2단계 후보 |
| NPC 감정 (`core.npc_emotion`, `npc-emotion*`) | 인물→인물 현재 감정 한 칸(덮어쓰기) | ○ | 인물끼리 관계는 1단계에서 초기값 고정 | 3단계 후보 |
| NPC 관계 기억 문 (`npc-relationship`, `relationship-mode`) | 인물끼리 기억을 켜고 끔, 관계만 모드 | ○ | 위와 같음 | — |
| 지각 (`perception.*`) | 누가 무엇을 실제로 보고 들었나, 비밀 | ✕ | 별도 큰 기능. 괴담 봇에 의미는 있으나 관계와 무관하고 비용이 큼 | 판단 지침에 「본 적 없는 일로 판정하지 않음」 한 줄만 |
| 불륜 의심 (`suspicion.*`) | 성인 연인 사이 의심 수치 | ✕ | 봇 주제와 무관 | — |
| 음란도·피임 (`openness.*`) | 성인 여성 인물 수치 | ✕ | 봇 주제와 무관, 미성년 인물이 있음 | — |
| 서사 리듬 (`rhythm.*`) | 장면 긴장·떡밥 회수 | ✕ | 카드 지침의 몫, 관계와 무관 | — |
| 관찰자 모드 (`observer-mode`) | 유저 캐릭터 없이 관전 | ○ | 우리 봇에 관전 모드가 생기면 그때 | — |

## 3. 옮기는 기능의 구체 설계

### 3-1. 관계 읽기 (리수폿 Writer의 축소판)

- **언제**: 본편 응답이 저장된 뒤(`onOutput`), 백그라운드. 설정으로 고름.
  - **매 턴**(추천 기본: 본편이 이 값을 쓰므로 늦으면 어긋남)
  - **N턴마다**(3/5턴, 비용 절약)
  - 수동·게임 열 때는 언제나 추가로 가능
- **모델**: 보조(기본) / 메인. 본편 응답과 별개 호출이라 본편 품질 영향 없음.
- **입력**: 직전 유저 입력 + 이번 응답(정리본), 등장 인물 짧은 시트(별명·가치관 2~3줄·지금 단계), 이미 기록된 사건, 계기 표. 짧은 시트는 **개발 때 로어북 요원 시트를 근거로 미리 만든 요약**을 쓴다(실행 중 로어북 전문을 넣지 않아 비용을 줄임). 괴담위키 문서는 컨텍스트용이 아니므로 근거로만 참고.
- **범위(1단계)**: 「유저가 그 인물에게 한 일」만(from = 인물, to = 유저). 되먹임 고리(주입 → 친절한 묘사 → 또 상승)를 막는 핵심 규칙이다. 인물이 먼저 친절하게 군 것은 점수가 아니다.
- **출력**: `{"events":[{"m","from","cue","quote","reason"}],"identity":{...}}`. 계기 이름은 3-3 표에서.
- **지침 본문**: 리수폿 「Affinity and Taste — Common Judgment」에서 다음을 옮긴다(영어 원문 축약).
  - 유저가 주인공이라는 사실은 호감 근거가 아니다. 모두를 유저에게 우호적으로 만들지 않는다.
  - 같은 행동도 그 인물의 가치관·관찰 기준으로 판단한다. 각자 이유가 달라야 한다.
  - 인사·외모·지위·일상 업무·답 없는 제안·이미 반영한 사건·회상은 점수가 없다. 정중한 거절은 잘못이 아니다.
  - 강요·위반·신체 반응을 호감의 증거로 보지 않는다.
  - 착취·조종 의도가 있으면 겉의 친절을 진짜 호감으로 바꾸지 않는다.
  - 본 적 없는 일(지각 경계)로 판정하지 않는다.
- 나머지(실패 처리·검사·쓰기 규칙)는 `docs/호감도_시스템_설계안.md` 4-3·8-3을 그대로 따른다.

### 3-2. 연출 주입 (리수폿 Director를 코드로)

- **언제**: 매 본편 요청(`onBeforeRequest`), 상태창 블록 뒤, 마지막 유저 메시지 앞.
- **누구**: 다음 중 하나에 해당하고 관계가 「무관심(보통)」이 아니거나 최근 단계가 바뀐 인물, 최대 5명.
  1. 이번 유저 입력·직전 응답에 이름·별명이 나옴
  2. 상태창 동행 칸
  3. 상황판에서 지금 장면 장소에 있는 요원
- **문장**: 리수폿 단계별 행동 설명(3-3 표)을 템플릿으로. 인물별 표현 정도(`express`)로 어미를 바꾼다.

```
[Relationship notes]
- 쟈알디 → {{user}}: Interest. Seeks shared time, offers reliable help and concern.
  Expression: very restrained — shows it through actions, not words. Keep rank and speech register.
- 스팡달 → {{user}}: Aversion (recent: hurtful words). Keeps distance, answers only as needed.
Background tendencies only. Do not mention scores. Do not create scenes about these notes.
```

- 숫자·모델이 쓴 인용은 넣지 않는다. 최근 이유는 계기 이름의 고정 번역만(「상처 주는 말」 등).
- 미성년 인물은 끌림·애정 단계 문장을 「믿고 따름·아낌」으로 바꾼다.
- 크기 상한 700자. 대상이 없으면 블록 자체를 넣지 않는다.

### 3-3. 점수 체계 (리수폿 것을 그대로)

**범위 −100 ~ 300, 8단계** (2판의 −100~100과 fieldrel 7단계는 버린다. 본편 연기용 단계 설명이 리수폿 쪽에 잘 다듬어져 있고, 필드는 아직 연결 전이라 바꿔도 손해가 없다.)

| 범위 | 단계 | 행동 방향 (주입 문장 원본) | 필드 대사 칸 |
| --- | --- | --- | --- |
| −100 ~ −71 | 극도의 적대 | 적대의 실제 원인을 유지. 단계만으로 해로운 행동을 만들지 않음 | hostile |
| −70 ~ −31 | 적대 | 성격대로 분명한 거리·적대 | hostile |
| −30 ~ −1 | 혐오(냉담) | 근거 있는 서운함·냉담, 짧은 대답 | hostile(약) |
| 0 ~ 60 | 무관심 | 기본 성격의 예의·잡담·업무 협조. 특별한 호의·냉대 만들지 않음 | 직급 칸 |
| 61 ~ 120 | 인식 | 개인적인 것을 기억, 없으면 알아챔, 질문이 조금 늘어남 | 직급 칸 + close 20% |
| 121 ~ 180 | 관심 | 같이 있을 시간을 찾고 믿을 만한 도움·걱정 | close 40% |
| 181 ~ 240 | 끌림 | 시간과 자리를 내주고 진심·약점을 더 보임 | close |
| 241 ~ 300 | 애정 | 깊은 배려, 자발적 지지, 정서적 친밀(성격 안에서) | close |

- 높은 단계도 **연애·반말·복종을 허락하지 않는다**(리수폿 원칙). 상관은 상관 말투 그대로.

**초기값 표** (리수폿 표 그대로, 실행 중 init 대신 개발 때 미리 채움)

| 관계 근거 | 초기값 |
| --- | ---: |
| 개인적 이력 없음, 같은 직무만 | 0 |
| 개인적으로 알고 지내는 친근한 지인 | 90 |
| 서로 도움이 확인된 믿는 동료·친구 | 150 |
| 뚜렷한 애착·감정적 개방 | 210 |
| 깊고 안정된 애정·헌신 | 270 |
| 개인적 냉담·풀리지 않은 원한 | −25 |
| 실제 적대 관계 | −60 |
| 깊고 분명한 원수 | −100 |

- 유저 초기값: 같은 조직 0. 적대 조직은 −25(냉담) 정도. 대사 칸이 이미 조직 적대를 표현하므로 점수로 이중 적대를 만들지 않는다.
- 인물→인물: 대사 JSON `relations` + 위키 근거로 위 표에서 고름(close → 90~150, hostile → −25~−60).

**변화량 = 계기 이름** (리수폿 값 그대로)

| 계기 | 값 | 뜻 |
| --- | ---: | --- |
| 작은친절 | +1 | 실제로 전해지고 받아들여진 작은 배려 |
| 도움 | +3 | 의미 있는 도움, 약속을 지킴 |
| 큰도움 | +5 | 대가를 치른 도움, 관계 회복, 중요한 신뢰 경험 |
| 헌신 | +10 | 드물고 결정적인 헌신·희생·약속 완수 |
| 실망 | −2 | 실제로 생긴 작은 실망 |
| 무시 | −4 | 분명한 무시·무례, 믿음에 금 |
| 배신 | −5 | 의미 있는 배신·굴욕 |
| 파탄 | −10 | 심각한 신뢰·관계 파괴 |
| 중대위반 | −50 | 예외. 명백하고 확정된 중대 위반 |

- 기준 메시지당 합 −10~+10(−50은 예외), 배율은 설정. 필드 행동도 같은 계기로: 선물 → 작은친절 또는 도움, 구해 줌 → 헌신, 폭력 → 파탄, 위협 → 무시.
- 신뢰 축은 리수폿에 없다. **두지 않는다**(2판의 신뢰 축 폐기 제안). 부탁 수락 문턱은 호감 단계로.

### 3-4. 호칭 기록 (리수폿 관계·호칭의 축소판)

- 대상: **인물 → 유저** 호칭·존댓말만.
- 기본값: 대사 JSON `address`(잼트리 → 후배)와 카드 설정.
- 바뀌는 조건(리수폿 규칙): 명시적 요청·허락(「말 편하게 해」), 받아들여진 관계 변화, 알려진 지위 변화(진급·전향), 실제 관계 파탄. **분위기나 점수만으로는 안 바뀐다.** 방향마다 따로.
- 관계 읽기 출력에 선택 칸 `address_change: {from, to_address, register: "반말|존댓말", quote}`를 더한다. 검사 통과 시 호칭 사건으로 장부에.
- 쓰임: 필드 대사 `{호칭}` 덮어쓰기, 본편 주입 문장에 「Address: '후배', informal」.
- 2단계 후보: 리수폿 「조짐 세기」(같은 방향 조짐 3번이면 변경, 묻기/자동).

### 3-5. 인물별 표현 정도

- `relations-base.json`에 인물별 `express` 0~3(0 = 거의 안 드러냄, 3 = 바로 드러남). 위키 성격 근거로 미리.
- 주입 문장 꼬리: 0 「shows it only through actions」, 1 「small, deniable cues」, 2 「visible but controlled」, 3 「openly」.
- 리수폿 원칙: 감정을 잘 숨긴다고 감정이 약한 게 아니다.

### 3-6. 화면

- 설정(채팅별): 관계 기능 / 읽기 빈도(매 턴·3턴·5턴·수동만) / 읽기 모델(보조·메인) / 본편에 반영(켬·끔, **기본 켬**) / 변화 속도 배율 / 추가 지침 한 칸.
- 관계 탭: 나를 보는 시선(8단계 막대, 최근 사건, 호칭), 인물끼리(초기값 표), 기록(사건·인용·취소·되살리기), 직접 수정(이유 필수)·고정, 「최근 N턴 다시 읽기」, 진단(마지막 10회).
- 게임: 이름표 옆 단계 아이콘, 변화 ↑↓.

## 4. 리수폿과 비용·구조 비교

| | 리수폿 | 우리 이식안 |
| --- | --- | --- |
| 매 턴 모델 호출 | 보조 3회(Router·Director·Writer) + 검색 시 추가 | **보조 1회**(매 턴 설정) 또는 N턴에 1회 |
| 본편에 끼우는 것 | 모델이 쓴 연출 메모(영어, 길다) | 코드 템플릿 관계 메모(최대 5명, 700자) |

| 인물 정보 출처 | 모델이 계속 고치는 인물 위키를 매 턴 끼움 | 본편은 지금처럼 캐릭터 로어북. 관계 메모만 추가 |
