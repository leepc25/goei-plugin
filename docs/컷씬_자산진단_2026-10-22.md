## 확인한 원인과 범위

현재 목록의 **10장면, 46컷, 592 PNG**가 모두 존재한다. 파일 번호, `timing.json`의 장 수·시간·루프 범위, 런타임 컷 길이, 640×360 해상도, 활성화된 오디오 참조 검사에서 누락은 없다. 따라서 현재 발견한 컷씬 정지는 단순한 파일 누락으로 설명되지 않는다.

실제 로딩 지연과 원본 시간표의 정지는 구분해야 한다. `first_day` c2/c3는 167/166ms 간격으로 약 6fps이며 c1/c4의 시작·끝 장은 각각 1,625ms 유지된다. 18초 중 6.5초가 500ms 이상 유지되는 장이다. `first_entry`는 20초 중 10.5초, `first_call`은 10초 중 5.375초가 이런 유지 프레임이다. 긴 정지가 연출 의도인지 불충분한 원본 동작인지는 시각 검수 대상이다. 코드에서 시간표만 빨리 돌리면 컷 길이와 자막이 어긋나므로 그렇게 바꾸지 않았다.

root 통합 담당은 재생 중 다음 컷 로딩을 기다릴 때 시간·자막·음성을 함께 멈추고, PNG 동시 디코딩을 제한하며, 컷씬 뒤 월드와 동일 장의 반복 그리기를 중단하는 수정을 진행했다. 이 자산 담당은 해당 런타임 파일을 변경하지 않았다.

## 크기와 메모리

요청 수는 장면을 처음 열 때 `index.json` 1회 + 컷별 timing + PNG를 모두 읽는 경우다. index는 이후 장면에서 공유 캐시가 가능하다. PNG 크기는 파일 합계이며 HTTP 압축·헤더는 제외했다. RGBA는 `장 수 × 640 × 360 × 4`의 디코딩 픽셀 하한 추정이며 브라우저 객체·GPU 복사·임시 버퍼는 추가된다.

| 장면 | 컷 | 장 | 첫 요청 수 | PNG MiB | 전체 장 RGBA MiB | 가장 긴 한 장 |
|---|---:|---:|---:|---:|---:|---:|
| opening | 9 | 105 | 115 | 8.89 | 92.29 | 2,750ms |
| first_day | 4 | 76 | 81 | 5.50 | 66.80 | 1,625ms |
| first_entry | 6 | 59 | 66 | 3.32 | 51.86 | 3,125ms |
| first_call | 3 | 24 | 28 | 0.80 | 21.09 | 3,125ms |
| attic | 4 | 64 | 69 | 5.00 | 56.25 | 167ms |
| three_years | 4 | 48 | 53 | 2.08 | 42.19 | 1,125ms |
| return | 4 | 76 | 81 | 5.74 | 66.80 | 625ms |

PNG 합계는 **40,683,070 bytes**다. 전 장면을 동시에 디코딩하면 픽셀만 약 520MiB이므로 전체 사전 디코딩은 피해야 한다. 한 장면 단위로 열고 종료 시 참조를 해제하며 다음 컷만 먼저 준비하는 방식이 맞다. 요청을 묶어도 픽셀 메모리는 줄지 않는다.

## 추가한 도구와 검증

`scripts/audit-cutscene-assets.mjs`는 기본 실행이 읽기 전용이다. 실제 TS 목록을 esbuild로 읽어 전달 자산과 비교한다. 오류가 하나라도 있으면 종료 코드 1이다. PNG 검사는 헤더/해상도 검사이며 픽셀의 시각 품질을 검사하지 않는다.

```sh
node scripts/audit-cutscene-assets.mjs --json /tmp/goei-cutscene-audit.json
node tests/cutscene-assets.test.mjs
```

`tests/cutscene-assets.test.mjs`의 4개 검사는 현재 전달 파일 전체, byte pack 복원, 목록/프레임/길이/오디오 누락 거부, 잘못된 시간/루프/PNG 헤더 거부를 확인한다. 테스트 임시 디렉터리는 정리한다.

## 선택형 전송 패키지 — 도구 구현, 런타임 미적용

같은 도구에 `--pack-dir`를 주면 원본 PNG 바이트를 그대로 연결한 `frames.bin`과 `manifest.json`을 장면별로 만든다. 동일 PNG만 SHA-256으로 중복 제거하고 각 컷은 원본 timing·loop·자막·장 순서를 유지한다. 크롭, 리사이즈, 색 변경, 중간 장 보간, 원본 덮어쓰기는 없다. 출력 경로를 원본 frames 폴더 안으로 지정하면 거부한다.

```sh
node scripts/audit-cutscene-assets.mjs \
  --scene first_day --pack-dir /tmp/goei-cutscene-packs
```

전체 장면 임시 패킹 결과:

- binary 합계 40,449,455 bytes, manifest 합계 87,715 bytes.
- 총 40,537,170 bytes. 현재 PNG 합계보다 약 0.36% 작을 뿐이며 파일 크기 압축 효과는 작다.
- 장면별 HTTP 요청은 manifest+binary **2회**로 묶을 수 있다. 원본이 81요청인 first_day의 요청 왕복 비용을 줄이는 목적이다.
- first_call은 24장 중 19개의 동일하지 않은 PNG를 저장하고, unpack 시 24장과 시간표를 byte 단위로 복원하는 테스트를 통과했다.
- 패킹 출력은 `/tmp`에만 만들었으며 게임 HTML, 기존 자산 폴더, 플러그인 릴리스에는 반영하지 않았다.

런타임 채택 시에는 manifest와 binary를 fetch → 길이/offset 검증 → `Blob.slice()`와 object URL → 기존의 제한된 수로 decode → 장면 종료 시 object URL 해제 순서로 연결한다. 기존 폴더 전달은 fallback으로 남겨야 한다. 플러그인에서는 외부 GitHub 의존을 늘리지 말고 같은 패키지를 자산 bridge를 통해 전달해야 한다. 첫 화면은 패키지 전체 다운로드 뒤 준비되므로 네트워크가 느린 환경에서는 컷 단위 패키지 또는 첫 컷 PNG 우선 방식과 실제 시간을 비교해야 한다. 이 연결은 아직 적용/검증하지 않았으며 재생 성능 개선 완료라고 주장하지 않는다.

## 다음 제작에 필요한 결정

먼저 버퍼링 수정판에서 남는 원본 동작의 끊김을 검수한다. first_day c2/c3의 실제 6fps 구간과 긴 시작/끝 정지 구간을 구분해 신규 제작 대상을 지정해야 한다. 6fps 원본을 복제·색 변경해 장 수만 늘리는 것은 새 동작 제작이 아니다. 신규 제작의 참조·통일성·과금 확인은 별도 PixelLab 담당이 수행한다. 이 문서는 비용이 드는 생성 회수를 추정해서 확정하지 않는다.
