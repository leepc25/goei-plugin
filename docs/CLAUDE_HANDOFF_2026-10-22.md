## 2. 사용자가 바꾼 제품 목표 — 확정

원래 게임은 채팅의 서브였는데 규모가 너무 커져 봇 완성이 어려워졌다. 현재 목표는 **글로만 보던 장소에 들어가 체험하고 인물을 직접 만나는 것**이다.

1. 사용자는 본편 채팅을 진행한다.
2. 봇의 요원 상태 추적 태그를 읽어 본부 안의 요원 존재·위치·활동을 결정한다.
3. 유저는 요원이 아니라 **자기 페르소나 캐릭터**를 조작해 본부를 방문한다.
4. 요원과의 대화는 고정 대사가 아니라 실제 모델 호출로 이루어진다.
5. 방문 중 대화 내용과 기록은 게임을 종료한 뒤 본편 컨텍스트에 남아 채팅을 이어갈 수 있어야 한다.

메트로배니아·로그라이크·전투·절차적 던전·파밍 확대는 **삭제가 아니라 보류**다. 기존 전투 시스템을 완성하는 방향으로 작업을 다시 넓히지 않는다. 당장 출동/전투용 수십 캐릭터·수십 동작의 전면 제작이 필요하지 않다.

## 3. 본부 미술과 상호작용 방향

### 과거 실패와 사용자 반응

- 초기 본부는 그림체, 가구 방향·비례, 문의 형태·공간 배치가 맞지 않아 사용자가 강하게 반려했다. 코드 실행이나 자동 테스트 성공은 미술 품질 합격의 근거가 아니다.
- `f7e096847f2549fbfe908affa8aa180f97ea5d7e`의 새 첫 방에는 사용자가 “훨씬 낫군”이라고 반응했다. 이것을 모든 본부 방의 최종 승인으로 확대하지 않는다.
- `6fe3844beaaf6ea236799de7b0d1fc8abadfe5de`에서 기존 앉기 클립을 의자에 맞춘 시도는 사용자가 “못쓰겠군”이라며 반려했다. 현재 코드에 남아 있는 것과 승인된 것은 다르다. 기존 인수인계서의 착석 구현 기록은 시각 승인 기록이 아니다.

### 새 제작 방식 — 사용자 제안에 따른 현재 방향

- 방 배경은 하나의 일관된 완성 이미지로 만든 뒤 필요한 오브젝트를 분리한다.
- 가구를 벽에 납작하게 붙인 것처럼 만들지 않는다. 바닥 접지·원근·방향·앞뒤 가림·충돌 위치가 맞아야 한다.
- 앉기 등은 임의의 캐릭터 동작을 임의의 가구에 매번 맞추기보다 **인물의 활동과 가구가 함께 맞춰진 에셋**을 제작하는 방향이다.
- 배경의 빈 가구와 인물+가구 에셋이 동시에 보이는 중복, 플레이어가 지나갈 때의 앞뒤 가림을 설계해야 한다. 레이어 전환 규격은 아직 미구현이며 검증해야 한다.
- 체격이 다른 모든 요원에게 모든 행동을 일괄 정렬하는 대규모 작업은 지금 하지 않는다. 공통 골격이나 체형별 자동 보정이 검증된 것처럼 설명하지 않는다.

### 논의된 생활 활동 — 후보 목록, 지금 전부 제작하라는 승인 아님

사용자가 예로 든 활동은 목욕, 화장실 이용, 샤워, 침대에 눕기, 의자에 앉기, 먹기, 쉬기 및 기타 상호작용이다. 이들은 요원/NPC의 본부 생활 표현을 위한 후보다. 현재 우선 제작 범위는 아래 남녀 페르소나 정적 기준 2장뿐이다. 구체적인 시설, 인물별 활동 배정, 장수와 예산은 확정되지 않았다.

## 4. 컷씬 방향 — 확정

사용자는 전체 이미지를 영화처럼 연속 재생하는 기존 방식의 심한 버벅임을 지적했다. **고전게임처럼 거의 정지된 장면에서 일부만 움직이는 방식**으로 바꾸기로 했다.

- 고정 배경과 인물 기본 자세를 두고 눈·입·손·문·빛 등 필요한 일부 레이어만 움직인다.
- 전체 화면 PNG를 대량 생성하고 갈아 끼우는 방식으로 확대하지 않는다.
- 첫 방에 맞지 않던 기존 `first_day` 자동영상은 첫 방 교체 때 제외됐다.
- 전체 컷씬이 새 방식으로 전환되거나 재생기가 완성된 상태는 아니다. 인물 구간과 신규 재생기 통합은 남아 있다.
- 현재 우선순위는 본부 방문과 본편 대화 연결이다. 컷씬 제작으로 인수 직후 범위를 넓히지 않는다.

## 5. 유저 페르소나 — 확정 범위와 미확정 사항

### 확정

- 남성/여성 각 1종으로 작은 범위부터 시험한다.
- 남성은 검정 바지정장, 여성은 검정 치마정장. 얼굴과 외형의 복잡한 커스터마이징은 당장 하지 않는다.
- 헤어 분리·조합 커스터마이징은 현재 시험 범위에서 제외했다. 기준 이미지 생성 사양은 남성 검정 짧은 머리, 여성 검정 단발, 흰 셔츠, 검정 구두다.
- 최초 선택은 저장되어 재입장 때 유지되어야 한다. 매번 다시 고르게 하지 않는다.
- **달리기는 필요하다.** 걷기만 구현하고 끝내면 사용자 요구를 충족하지 못한다.
- 원본 세로 상한 256px으로 시험한다. 남녀 정적 기준부터 보고 이후 늘린다.

### 이후 동작 계획 — 제안이며 추가 생성 승인 아님

이전 계획안은 각 인물 대기 4프레임, 걷기 8, 달리기 8, 상호작용 4, 합계 24프레임이었다. 남녀 합계 8클립/48프레임이지만 이것을 제작 발주나 확정된 최소 장수로 취급하지 않는다. 방향 수·회전·좌우 반전·최종 프레임 수는 테스트 후 결정한다.

### 아직 정해야 할 구현 세부

- 선택 저장 범위: Risu 유저 페르소나별/카드별/채팅별 중 정확한 키는 미확정. 다른 페르소나에 선택이 잘못 덮어씌워지지 않도록 설계하고 최초 한 번 선택·재입장 유지부터 검증한다.
- 신규 캐릭터 실제 표시 배율·바닥 기준점은 이미지 검수 후 확정한다.
- 정적 1장만으로 걷기·달리기가 완성된 것처럼 발표하지 않는다.

비교 배경은 지정 HTML의 room/workstation을 추출하여 기존 합성 좌표를 따른 것이다. 옅은 발밑 그림자는 검토용 합성이며 PNG 원본에는 없다.

### 실제 생성 정보와 비용

- 도구: PixelLab MCP `create_image_pro_flash`, `output_count=1`씩 총 2회.
- 설정: `width=128`, `height=256`, `no_background=true`, `max_colors=48`, custom size Beta.

- 별도 direction/view 필드가 없어 프롬프트에 오른쪽 3/4, 눈높이 횡스크롤 시점, 탑다운 아님을 명시했다. 실제 결과도 오른쪽 3/4라는 제작자 보고다.

## 7. 해상도와 크레딧에서 혼동하지 말 것

- 기존 쟈알디 동작 생성 프레임은 192×144였다. 실제 대기 인물 알파 높이는 약 98~99px이고 게임 내부 렌더 배율은 2.75였다. 생성 캔버스, 불투명 인물 크기, 게임 렌더 크기는 서로 다르다.
- 사용자가 기존 품질과 배경 부조화를 지적한 뒤, 검증 없이 128px로 낮추자는 추천은 철회했다. 현재 결과는 **128폭×256높이**이며 “128px 캐릭터로 확정”이 아니다.
- 신규 원본에 2.75배를 그대로 적용하면 너무 커진다. 남녀에게 서로 다른 확대를 줘 억지로 같은 키로 맞추지 않는다.
- 구독 `Generations`와 충전 `Credits`는 다른 단위다. 공식 구매 UI 확인 당시 **1 credit = $1 USD**이며 1 credit=1 generation이 아니다.
- 공식 요금표의 Text v3 256×256/8프레임 예상값은 `$0.0302`였으나 도구별 요금이며 실제 처리 시간 등에 따라 달라질 수 있다. 이번 Pro Flash 두 장의 비용은 위 실제 18 generations 영수증을 따른다. 과거 48 generations 계획을 48달러로 환산하지 않는다.
- 현재 가격과 기능은 생성 직전 공식 문서 및 MCP capabilities/balance로 다시 확인한다. 가격 예시를 모든 도구에 일괄 적용하지 않는다.

공식 자료: [API 요금](https://www.pixellab.ai/pixellab-api), [API 문서](https://api.pixellab.ai/v2/docs), [OpenAPI](https://api.pixellab.ai/v2/openapi.json), [MCP 안내](https://api.pixellab.ai/mcp/docs).

## 8. 봇 플러그인 연결 — 실제 구현 상태

게임은 이미 별도 코드 팩으로 플러그인에 탑재되는 구조다. 새 앱이나 별도 모델 서버를 처음부터 만들 필요가 없다.

```text
플러그인 게임 버튼 (src/ui/game.ts)
  → 게임 코드 팩 (src/game/entry.ts → play.ts → action/main.ts)
  → GameBridge.visit (src/game/bridge.ts)
  → 방문별 호스트 (src/host/game/visit.ts)
  → 기존 Risu runModel (src/host/llm.ts)
  → 원래 채팅의 방문 기록 + 컨텍스트 로어북
```

| 부분 | 현재 상태 |
| --- | --- |
| 본부 방문 진입 | bridge.visit가 있으면 기존 본부로 바로 시작 |
| 방문 대화 UI | 「본부 인물 · 대화」 및 기존 인물 상호작용 지점에서 열림 |
| 모델 호출 | 메인/보조 선택, 사용자 전송 시에만 호출, 자동 재시도 없음 |
| 요청 재료 | 요원 로어북/CBS, 요원 상태·상황, 유저 이름·페르소나, 최근 본편 6마디, 해당 요원 최근 8회 대화, 본부 기록 발췌 |
| 본편 복귀 기억 | 성공 응답마다 즉시 기록. 종료 이벤트에만 저장을 맡기지 않음 |
| 대화 원문 저장 | 해당 채팅 `goeiHqVisitV1`에 최근 100회 |
| 본편 컨텍스트 | 항상 활성인 「본부 방문 대화 기록」 로어북에 최근 8회 발췌, 발언당 유저 700자/요원 1400자 제한 |
| 채팅 분리 | 방문 시작 카드/채팅에 묶음. 요청 도중 채팅 변경 시 원래 채팅에 저장, 이후 요청은 재입장 요구 |
| 상태 갱신 | 모델 발언의 태그·보상 명령은 실행하지 않음. 본편 요원 상태 직접 변경 없음 |
| 방문 중 전투 | 출동·이전 전투 저장 복원 차단. 독립 액션 데모는 과거 모드 유지 |
| 실제 NPC 배치 | **미완료.** 방 분류는 데이터/목록만. 스프라이트 이동·활동 적용은 아직 아님 |
| 신규 페르소나 | **미완료.** 선택 저장·그림 적용·움직임 연결 필요 |

현재 상태 매핑은 구현상의 초기 선택이다: 내근/대기→사무실, 휴게→휴게실, 부상→의무실. 외근·비번·격리·작전투입·실종·사망·미정/잠긴 요원은 대화에서 제외한다. 이것은 모든 생활 태그나 정확한 위치 해석이 완성됐다는 뜻이 아니다. 실제 봇 태그 체계와 대조하고 확장한다.

요원 설정이 없으면 대화를 중단한다. 대화창은 텍스트로 응답을 표시한다. 본편 메시지 목록에 별도 가짜 유저 메시지를 끼워 넣지 않는다. 로어북 저장은 현재 구현 방식이며 사용자가 구체적 저장 스키마까지 지정한 것은 아니다.

## 9. 검증한 것과 검증하지 못한 것

완료된 검증:

- 최초 본부 통합 빌드·타입 검사, 전체 테스트 **58개 파일** 통과. 테스트 사례 58개라는 뜻은 아니다.
- main v0.16.40 병합 후 타입 검사 및 영향 범위 `visit`, `gamelink`, `imgtag`, `npc` 테스트 파일 재검증 통과.
- 호스트 모의 테스트: 모델 선택, 중복 요청 차단, 부재 요원 차단, 모델 실패 시 기록 미생성, 요청 도중 채팅 전환 시 원래 채팅에만 기록.
- Chromium 모의 브리지: 본부 입장→대화창→부재 인물 비활성→전송→저장 상태 표시. 브라우저 JS 오류 없음.
- 시험판 패키지 생성 완료.

미검증/주의할 실제 경계:

- 실제 사용자의 Risu 모델 연결·본편 다음 응답에서 기록 참조는 아직 실행하지 않았다. 모의 응답 검증을 실제 모델 검증이라고 보고하지 않는다.
- 창을 닫아도 이미 전송한 모델 요청은 계속될 수 있다. 취소 API를 연결하지 않았다.
- 저장 실패·탭 종료 등에서 미저장 응답을 영구 복구하는 큐는 구현하지 않았다. 필요하면 유료 재호출 없이 복구할 수 있게 후속 보완한다.
- 채팅 식별은 인덱스와 제공되는 카드/채팅 ID를 사용한다. 실제 Risu의 ID 제공·삭제/재정렬 동작도 로컬에서 확인한다.
- 현재 컨텍스트는 한정된 원문 발췌이지 장기 요약/무제한 대화 보관이 아니다.
- 이전 NPC/전투 기능과 UI 흔적 전체를 정리한 상태는 아니다. 새 방문 모드에서 과거 행동이 노출되는지 실사용 검증한다.
- 신규 남녀 PNG를 이 세션에서 열어보거나 적용하지 않았다. 기존 캐릭터 렌더링은 새 페르소나의 완료 근거가 아니다.

## 10. Claude가 바로 할 일 — 순서

1. 로컬 변경을 보존하고 작업 브랜치를 인수한다. 최신 main과 분기 상태를 확인한다. 이 문서와 `본부_방문_모델연결.md`를 먼저 읽는다.
2. 실제 Risu에서 시험판을 열어 **본부 입장 → 실제 모델 대화 → 종료 → 본편 기록 참조** 한 흐름부터 끝까지 확인한다. 로어북 활성 여부와 다른 채팅 오염 여부도 확인한다. 코드가 이미 있으니 새 시스템을 다시 짓지 않는다.
3. 로컬 폴더의 남녀 원본과 두 배율 비교 이미지를 직접 열어 사용자에게 검수 결과를 보여준다. 추가 생성 없이 먼저 확인한다.
4. 남녀 페르소나 선택·지속 저장과 승인된 정적 이미지 연결을 구현한다. 재입장 때 선택 유지, 크기·접지·가림을 실제 본부 화면에서 확인한다.
5. 상태 태그에 따른 실제 NPC 방 배치를 연결한다. 처음에는 적은 인원과 현재 필요한 상태만. 존재하지 않는 동작·가구 조합을 완성품처럼 넣지 않는다.
6. 기준 2장 확인 후 걷기·달리기 등의 필요한 동작을 같은 외형으로 확장한다. 사용자 검수 전 대량 생성하지 않는다.
7. 운영 릴리스는 테스트 결과와 실제 반영 범위를 구분해서 배포한다. 테스트용 가짜 모델 응답이 운영 코드 경로에 남지 않게 확인한다.

새로운 완성 날짜나 예산은 합의되지 않았다. 과거 사용자의 “1시간 남았다” 발언을 지금 시점의 일정으로 재사용하지 않는다. 먼저 좁은 실제 작동 흐름을 보여주고 다음 범위를 잡는다.

## 12. 협업 방식

사용자는 실행 환경과 설명을 계속 바꾸거나 “실패했다”는 보고만 반복하는 것에 강하게 불만을 표했다. 실제 파일·코드·화면을 확인하고, 작동한 결과와 미완료 부분을 구분해 말한다.

PixelLab 생성은 인증된 로컬 제작 환경에서, 코드 통합도 원본 파일을 볼 수 있는 로컬 Claude에서 이어가는 방향이다. 클라우드에서 로컬 `C:/...` 경로를 읽을 수 있다고 가정하지 않는다. 같은 2장을 다시 만들거나 인증을 처음부터 반복할 필요가 없다.

과거 사용자는 병렬 작업과 세션 분리를 요청했지만 현재 역할은 **Claude가 통합 책임을 맡아 좁은 완료 흐름을 확보하는 것**이다. 분담하더라도 담당 파일·산출물·비용 범위를 정하고 통합 담당이 실제 검수한다. 이 문서를 제작 승인 범위 확대나 무제한 병렬 생성 승인으로 해석하지 않는다.
