# 구현 가능성 검토 · 2026-10-20

작성: Claude / 상태: 기획서 0.3 전 항목을 현행 코드와 RisuAI 플러그인 제약에 대조한 결과. 사용자 질문 "구현 가능성 여부는 검토한 건가"에 대한 답이다.

판정 기준: **가능**(현행 구조 안에서 됨), **조건부**(되지만 제약·선행 작업·외부 의존이 있음), **위험**(설계를 바꾸거나 범위를 줄여야 할 수 있음).

## 0. 결론

- 기획서의 시스템 대부분은 **가능**이다. 전투·방·생성·지도·본부·대사·저장·연동은 전부 코드와 데이터로 풀리고, 현행 `src/game/action/`(약 1,700줄, 1방·1요원·적 4체·입력 3종·30Hz 판정·경직/다운/무적/슈퍼아머·아이템·자동 전투·pluginStorage 저장·Playwright 시험)이 그 출발점이 된다.
- **위험 3개**: (1) 그림 용량과 디코딩 메모리(8명 전부 동시 상주는 불가 → 선택 요원만 받고 디코딩), (2) 탐사·규칙 자동 진행 AI(전투 AI는 있으나 탐사 AI는 없음 → "규칙서에 있는 것만 아는 보수적 AI"로 범위 고정), (3) PixelLab 비용(잔액 10, 요원 1명 1단계 60~150 → 충전 없이는 그림 단계 진입 불가).
- **조건부 4개**: 코드 용량(게임 본체를 별도 조각으로 내려받기), 한글 픽셀 폰트(용량 때문에 시스템 글꼴 폴백), 본편 쓰기 연동(sendChat 실기 미확인), GPT 컷신 그림(Codex 왕복 의존).
- 회색 상자 시험판(그림 없이 한 바퀴)까지는 전부 **가능**이고 외부 의존이 없다. 그래서 순서를 그림보다 앞에 둔 것이 맞다.

### 2.5 자산·용량·성능 (**위험 1**)

| 항목 | 판정 | 수치 |
| --- | --- | --- |
| 그림 팩 총량 | **위험** | 요원 1명 180~200장 × PNG 약 5KB = 0.9~1MB. 8명 = 7~8MB > 예산 5MB. 적·보스·배경·소품·컷신 별도. |
| 대응 | — | (a) 여백 트리밍+아틀라스로 1/2, (b) **요원별 팩을 따로 받기**(선택한 요원만, 16.3), (c) 괴이별 팩 분리. 코드 쪽은 actionpack.ts 다중 키로 확장. 이렇게 하면 동시에 받는 양은 "코어 + 요원 2 + 괴이 1" ≈ 3MB |
| 디코딩 메모리 | **위험** | 160×160 RGBA = 102KB/장. 요원 1명 190장 = 19MB, 적·배경 포함 한 장면 40~50MB > 16.4의 32MiB 목표. 트리밍(실제 몸 60~90×128 ≈ 40KB/장)으로 1/2.5, 선택 요원만 디코딩, 아머·인형은 쓸 때만 디코딩 → 20~25MB로 가능 |
| pluginStorage base64 | 조건부 | ×1.33 팽창. 3MB 팩 = 4MB 문자열. 현행 patrol 704KB·action 472KB는 문제 없었음. 수 MB는 실기 확인 필요(순찰 팩 때 미측정) |
| 성능 | 가능 | 벨트스크롤 한 화면 적 8~12, 투사체 20, 효과 30 수준은 30Hz 판정+RAF로 충분(현행 측정 60fps). 공간 분할은 보스전·난입(세 갈래 20체)에서만 필요 |
| 게임 코드 용량 | **조건부** | 본체 goei-body가 이미 약 1MB(200KB 조각 6개). 16.4의 게임 추가 250KiB 안에 "본부+생성+전투+대사 데이터"는 안 들어감(추정 400~600KiB minify). 대응: 게임을 **별도 조각 묶음**(goei-game.N.txt)으로 두고 게임 창을 열 때만 받기. 로더(src/main.ts)가 이미 조각 내려받기·버전 비교를 함 |
| 단일 HTML 시연판 | 가능 | 현행 빌드가 그림 인라인 HTML을 만듦(247KB). 2명+1괴이면 3~4MB HTML, 열림 |
| 한글 픽셀 폰트 | **조건부** | OFL 갈무리체 서브셋(한글 2,350자)도 woff2 약 150~300KB. 게임 조각에 넣으면 허용 범위지만 플러그인 본체엔 안 넣음. 폴백은 시스템 글꼴(현행) |
| 소리 | 가능 | Web Audio 합성. 코드에 아직 없음(risuai.d.ts에 AudioContext 언급만). iframe에서 사용자 입력 뒤 AudioContext 생성 필요 → 첫 키 입력에서 생성 |

## 4. 범위를 줄여야 할 때 먼저 빼는 것

1. 로제몬 인형(아군 개체) → 요원 8번째 그대로.
2. 3층 미로 → 두 번째 판.
3. 본부 걷기 화면 → 메뉴만으로 시작, 걷기는 나중.
4. 2인 대화 사건 → 조합 3개부터.
5. 한글 픽셀 폰트 → 시스템 글꼴.
6. 보고서 입력칸 삽입 → 복사 버튼.
7. 세 갈래 싸움 → 난입을 "플레이어만 공격"으로 시작.

## 5. 아직 측정하지 못한 것 (실기 확인 필요)

- RisuAI 안에서 수 MB pluginStorage 쓰기·읽기 시간과 안정성(순찰 팩 704KB까지만 경험).
- 모바일 실기(가로 모드) 프레임·터치.
- 장시간 메모리 누수(팩 교체 반복).
- sendChat/입력칸 접근.
- Web Audio가 Risu iframe에서 허용되는지.

이 다섯은 회색 상자 시험판을 실제 플러그인에 넣어 돌리는 순간 같이 측정한다.

### 5.1 가짜 팩 부하 시험 (사용자 지적 2026-10-20: 회색 상자로는 메모리 부하를 못 잰다)

메모리는 그림의 내용이 아니라 "몇 장을 어떤 크기로 펼쳐 뒀나"로 정해지므로 실제 도트 없이 잰다.

- 코드로 노이즈 PNG를 실제 규격(요원 190장 × 캔버스, 트리밍 크기, 적·수호자·층 유형 타일셋은 스테이지 설계서 14장 장수)대로 만들어 GOEIPACK으로 묶는다. 노이즈는 압축이 안 되므로 파일 용량은 실제보다 크게(보수적) 나오고 펼친 메모리는 같다.
- 실제 경로로 돌린다: 내려받기 → pluginStorage 저장(base64) → 읽기 → 디코딩 → 층 유형 팩 교체 10회.
- 잰다: 저장·읽기 시간, 디코딩 뒤 램 증가(Chromium `performance.measureUserAgentSpecificMemory` 또는 CDP, Playwright 자동), 교체 반복 뒤 누수, 모바일 Chrome 실기.
- 128px(160 캔버스)과 96px(128 캔버스) 두 규격으로 돌려 숫자를 비교한다. 해상도 결정(결정 목록 A20)은 회색 상자의 크기 비교(보기)와 이 숫자(부하)를 같이 보고 한다.
- 시험판 안에 「부하 시험」 버튼으로 넣는다.

실측(2026-10-20, 사용자 PC 브라우저, `release/demo/goei-graybox.html` 부하 시험, 요원 2×190장 + 적 8×40장 + 타일셋 5 = 705장, 가짜 도트는 16색 덩어리):

| 규격 | PNG 합계 | base64 | 펼친(디코딩) 램 | 저장 | 읽기 | 디코딩 | 층 교체 10회 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 128px (캔버스 160) | 2.5MB | 3.3MB | 51.0MB | 71ms | 100ms | 116ms | 501ms |
| 96px (캔버스 128) | 1.8MB | 2.3MB | 36.3MB | 52ms | 74ms | 101ms | 476ms |
| 80px (캔버스 96) | 1.5MB | 2.0MB | 24.9MB | 39ms | 55ms | 102ms | 461ms |

판단: 셋 다 PC에서는 여유. 96px은 램 29% 절감이지만 시간은 거의 같다. 결정 A20은 128 유지로 추천하고, 폰 실기에서 128이 버벅이면 그때 96을 재검토한다. 플러그인 창(RisuAI iframe)과 본편 채팅이 같은 탭에서 램을 나눠 쓰므로 실제 한도는 더 낮게 봐야 하며, 그 수치는 플러그인 안에 넣은 뒤 잰다.
