## 0. 전제 바로잡기

### 0-1. 앞선 두 문서의 틀린 전제
1. 「카드 위키가 정본이라 컨텍스트에 들어간다」 → **틀림.** 괴담위키(`WIKI｜` 항목)는 비활성이라 모델이 못 본다. 본편 모델이 보는 인물 정보는 **캐릭터 로어북의 요원 시트**이고 플러그인이 장면에 맞게 자리 항목(`goei_lore_agent`)에 넣는다.
2. 「로어북이 있으니 인물 정보는 됐다」 → **틀림.** 로어북은 **죽은 정보**다. 채팅이 100턴 진행돼도 쟈알디 시트는 첫날 그대로다. 리수폿의 진짜 가치는 **인물 정보가 이야기에 따라 갱신**되는 것이다.
3. 「요원 태그·확정 사항이 상태를 맡는다」 → **반쪽.** 태그(`쟈알디|부장|부상|…`)는 **신호**다. 왜 다쳤는지, 누구 때문인지, 그 뒤 태도가 어떻게 바뀌었는지는 담지 않는다.
4. 「성격·기본정보는 로어북에 있으니 빼자」 → **틀림.** 그것도 바뀐다(3번과 같은 이유).

### 0-2. 바로잡은 목표
- 채팅마다 **살아 있는 인물 기록**을 둔다. 로어북 시트는 **시작값**일 뿐이다.
- 기록은 리수폿 인물 문서의 칸을 **전부** 가진다: 기본정보·성격·현재 상태·인간관계·말투·행동 경향·아는 정보·목표와 미해결·주요 행적·현재 장면 + **호감 수치** + **호칭**.
- 본편 모델은 장면에 나온 인물의 **살아 있는 기록**을 받는다(죽은 시트 대신 또는 덧붙여).
- 필드 게임은 같은 기록(호감·호칭·상태)으로 대사·태도를 정한다.
- 태그·확정 사항은 기록을 **갱신하라는 신호**로도 쓴다.

## 1. 리수폿은 실제로 무엇을 얼마나 쓰나 (실측)

### 1-1. 한 턴의 호출과 고정 지침 크기 (호감+관계·호칭만 켠 상태, 자료·대화 제외)

| 단계 | 시점 | 고정 지침 | 더해지는 자료 | 비고 |
| --- | --- | --- | --- | --- |
| ① Router | 본편 **앞** | 약 650 tok | 위키 목록(제목·별명·태그), 최근 대화 | 문서 최대 6개 고름 |
| ② Director | 본편 **앞** | 약 12,000 tok (핵심 1,900 + 출력 계약 700 + 호감 규칙 6,800 + 관계·호칭 규칙 2,700) | 고른 위키 본문 최대 16,000자(≈ 한국어 8,000~16,000 tok), 최근 대화 | 자료 모자라면 검색 요청 뒤 **한 번 더** |
| ③ Main | 본편 | (카드) | + Director 메모 + 위키 참조(최대 16,000자) | 본편 입력이 매 턴 4,000~16,000 tok 늘어남 |
| ④ Writer | 본편 **뒤** | 최대 약 38,000 tok (핵심 7,000 + 출력 계약 6,300 + 슬롯 정의 8,800* + 수치 정책 4,200* + 호감 규칙 7,900 + 관계·호칭 3,700) | 이번 응답, 이전 대화 최대 16,000자, 관련 위키 | *슬롯·정책은 켠 기능만 보내서 실제는 줄어듦. 그래도 20,000 tok 이상 |

- **매 턴 추가 입력 합계: 대략 60,000~100,000 tok**(보조 모델 쪽) + 본편 입력 4,000~16,000 tok 증가.
- **지연**: ①②가 본편 앞에 **직렬**로 돈다. 보조 모델 응답 2회를 기다린 뒤 본편이 시작된다(검색 요청이 있으면 3회).
- 저장: 플러그인 저장소에 인물 문서 전체. 다시 굴리기는 「같은 자리 새 chatId」로 감지해 이전 기록을 되감는다(`auto-wiki` V29).

### 1-2. 인물 문서의 칸 (옮길 대상)

| 칸 | 리수폿 id | 내용 |
| --- | --- | --- |

### 2-3. 「성능 차이가 없다」는 말의 참·거짓

- **참인 부분 — 기록 품질.** 기록을 쌓는 건 어느 안이든 「본편 응답을 읽고 JSON으로 변화를 내는 보조 모델 1회」다. 같은 모델에 같은 규칙이면 결과가 거의 같다. 리수폿 지침이 긴 이유는 설명·예시·6개 기능 공용 틀 때문이고, 호감·관계·인물 기록만 남기면 규칙 수는 그대로 두고 길이를 1/5로 줄일 수 있다.
- **거짓인 부분 — 비용·지연.** 안 ①은 보조 입력이 턴당 6~10만 tok, 본편 앞에 직렬 2회다. 안 ②는 1~1.6만 tok, 본편 뒤다. **5배 차이**이고 유저가 기다리는 시간은 0 vs 수십 초다.
- **거짓인 부분 — Director.** 안 ②는 Director가 없다. 「본편 응답이 기록을 얼마나 잘 살리나」에서 ①이 낫다. 특히 **지식 경계**(이 인물은 그 비밀을 모른다)는 기록을 주기만 해서는 본편 모델이 종종 어긴다. 그래서 안 ③(짧은 Director)을 **켜고 끄는 선택**으로 둔다.
- 결론: **기록은 ②로 충분하고, 연출은 필요한 사용자만 ③을 켠다.** ①을 그대로 넣는 이유는 없다(필드 연동 불가, 우리 요청 가공과 충돌, 5배 비용).

## 3. 데이터: 살아 있는 인물 기록

### 3-1. 저장 위치와 구조

`chat.goeiPeopleV1` (채팅 객체 최상위 키. `goeiFieldV1`·`goeiHqVisitV1`과 같은 방식. 복제·분기 시 같이 따라감)

```ts
interface PeopleStore {
  schema: 1;
  people: Record<string, Person>;        // 열쇠 = 위키 표기 이름 (쟈알디)
  log: Change[];                          // 변경 기록 (최대 800건, 접기 3-5)
  read: Record<string, string>;           // 읽은 메시지: chatId(또는 #순번) → 내용 해시
  identity: { faction: string; rank: string; level: number | null; from: 'status' | 'scan' | 'default'; anchor: string };
  migrated?: string[];
}
interface Person {
  name: string;
  seeded: { from: 'lore' | 'dialogue' | 'none'; at: string };   // 시작값 출처
  slots: Record<SlotId, Entry[]>;         // 아래 칸 목록
  affinity: { base: number; pin?: number }; // 유저 대상 호감. 현재값은 log에서 계산 (3-4)
  address: { toUser: string; register: '존댓말' | '반말' | '혼합'; pin?: boolean };
  express: 0 | 1 | 2 | 3;                 // 감정 표현 정도 (시작값 표)
  minor?: boolean;
}
type SlotId = 'identity' | 'personality' | 'state' | 'relationship' | 'speech' | 'behavior' | 'knowledge' | 'threads' | 'history' | 'scene';
interface Entry {
  id: string;                             // 항목 id (갱신·고정·취소 대상)
  text: string;                           // 한국어, 항목당 200자 이하
  target?: string;                        // relationship·speech: 대상 ('@user' 또는 이름)
  anchor: string; seq: number;            // 이 내용을 확정한 기준 메시지 + 순서
  quote?: string;                         // 근거 인용 60자 (seeded 항목은 없음)
  pin?: boolean; void?: boolean;
  replaces?: string;                      // 이 항목이 대체한 이전 항목 id (이력)
}
interface Change {                        // 호감 계기·호칭 변경·항목 갱신의 공통 기록
  id: string; anchor: string; seq: number; src: 'story' | 'field' | 'fieldtalk' | 'manual';
  who: string; kind: 'cue' | 'address' | 'entry';
  cue?: Cue; quote?: string; reason: string; void?: boolean; pin?: number;
}
```

- **항목(Entry) 단위**로 갱신한다(리수폿 `entry_ref`와 같음). 「현재 상태」 칸에 항목이 3개면 바뀐 하나만 교체한다. 문서 전체를 다시 쓰지 않아 모델 출력이 짧고, 사람이 고정·취소하기 쉽다.
- `scene`·`history`는 길어지기 쉬워 항목 수 상한(scene 3, history 12, 나머지 8). 넘으면 오래된 항목을 코드가 한 줄로 합친다(3-5).
- `npc_emotion`(인물끼리 감정)은 1단계에서 **두지 않는다**(아래 6-2 결정 사항).

### 3-2. 시작값 (로어북 시트 → 기록)

- **시점**: 그 인물이 채팅에서 **처음 등장**할 때(이름·별명이 응답에 나옴, 또는 상황판 태그에 나옴) 한 번.
- **방법 (비용 0)**: 로어북 요원 시트는 제목 있는 절로 되어 있다. 코드가 절 제목을 칸에 대응시켜 그대로 넣는다(기본정보·성격·말투·행동·인간관계·아는 정보). 대응표는 개발 때 시트 구조를 보고 만든다. 절이 없는 칸(현재 상태·목표·행적·장면)은 비워 둔다.
- **호감 시작값**: `relations-base.json`(개발 때 위키·시트 근거로 작성, 리수폿 초기값 표의 값: 0 / 90 / 150 / 210 / 270 / −25 / −60 / −100). 유저 대상은 조직×조직 표(같은 조직 0, 적대 조직 −25).
- **호칭 시작값**: 대사 JSON `address` + 유저 신분(직급 비교).
- 로어북에 없는 인물(사용자가 만든 NPC)은 `seeded.from = 'none'`으로 빈 기록을 만들고 이후 갱신으로 채운다.
- **시트는 영어**(카드 로어북)다. 시작값으로 넣을 때 영어 그대로 두고, 갱신기가 **한국어 항목으로 교체**해 가게 한다(모델 1회 호출로 미리 번역하는 선택지도 둔다. 인물당 1회, 처음 등장 때만).

### 3-3. 기록 갱신 (리수폿 Writer의 축소판) — 매 턴 보조 1회

- **시점**: 본편 응답이 저장된 뒤(`onOutput`), 백그라운드. 설정으로 「매 턴 / N턴마다 / 수동+게임 열 때」. **기본 매 턴**(본편이 이 기록을 쓰므로 늦으면 어긋남).
- **대상 인물**: 이번 응답·직전 입력에 이름·별명이 나온 인물 + 동행 칸 + **태그가 바뀐 인물**(상태 태그 변화는 「경위를 기록할 것」 지시로 덧붙임). 최대 6명.
- **입력**(약 10,000~16,000 tok): 압축 지침(5,000) + 대상 인물의 현재 기록(인물당 400~800자) + 직전 한 쌍(맥락용, 근거 금지) + 이번 응답(정리본: 상태창·상황판 태그·플러그인 지시문 제거) + 계기 표 + 이미 기록된 변경(중복 방지).
- **출력** (한 JSON):

```json
{
  "entries": [
    {"who":"쟈알디","slot":"state","op":"upsert","replace":"e12","text":"왼팔 부상. 3일차 명일 아파트에서 유저를 감싸다 다침","m":"m2","quote":"팔을 감싸 안았다"},
    {"who":"쟈알디","slot":"knowledge","op":"add","text":"유저가 가짜 관리국 내통자 명단을 봤다는 사실을 들음","m":"m2","quote":"명단을 봤어"},
    {"who":"쟈알디","slot":"threads","op":"remove","replace":"e07","m":"m2","quote":"약속은 지켰어"}
  ],
  "cues": [{"who":"쟈알디","cue":"큰도움","m":"m2","quote":"팔을 감싸 안았다","reason":"유저가 몸으로 막아 줌"}],
  "address": [{"who":"쟈알디","toUser":"너","register":"반말","m":"m2","quote":"이제 그냥 너라고 할게"}],
  "identity": {"faction":null,"rank":null}
}
```

- **지침에 옮기는 리수폿 규칙**(압축, 영어): 확정된 RP만 근거(직전 대화·요약·회상은 근거 아님) / 사건·상태 변화·인물별 지식·지속 사실·미해결·갱신 대상 6관점 / 말하지 않은 감정·동기를 사실로 만들지 않음 / 지식은 실제로 보고 들은 것만 / 미해결을 완료로 바꾸지 않음 / 바뀐 항목만, 유효한 사실은 유지하고 짧은 새 근거로 기존 약속을 지우지 않음 / 호감은 유저가 한 일만, 인사·외모·직위·일상 업무는 점수 없음, 각자 가치관으로 판단 / 호칭은 명시적 허락·관계 변화·지위 변화·파탄 때만.
- **검사(코드)**: who가 명단(별명 포함)에 있나 / slot·cue가 표에 있나 / quote가 그 메시지 원문에 있나 / replace가 실제 항목 id인가 / 인물당 항목 8개·계기 2개 이하 / 텍스트 200자. 어긋난 것만 버린다. JSON 실패는 「JSON만, 더 짧게」 1회 재요청.
- **쓰기 규칙**: 본편 응답 대기 중이면 보류, 쓰기 직전 같은 채팅인지 확인, 덧붙이기만(길이 변화로 버리지 않음), 작업은 한 번에 하나(괴담톡·괴담넷 뒤).

### 3-4. 호감 계산 (리수폿 수치 체계 그대로)

- 범위 −100~300, 8단계(극도의 적대 / 적대 / 혐오 / 무관심 / 인식 / 관심 / 끌림 / 애정), 단계 상한 −71/−31/−1/60/120/180/240/300.
- 계기 → 값: 작은친절 +1, 도움 +3, 큰도움 +5, 헌신 +10, 실망 −2, 무시 −4, 배신 −5, 파탄 −10, 중대위반 −50(예외). 기준 메시지당 합 −10~+10, 배율 설정(0.5~2).
- **현재값 = 시작값 + 살아 있는 계기의 합**(순서대로, 상한 적용) → pin 있으면 그 값. 매번 재계산(저장된 delta 없음).
- 살아 있는 계기 = 기준 메시지가 있고 인용이 아직 그 메시지에 있음(story) / 기준 메시지가 있음(field) / 항상(manual).
- 필드 행동 → 계기: 선물 → 작은친절·도움, 구해 줌 → 헌신, 폭력 → 파탄, 위협 → 무시. 필드 대화 태그 `[[관계 계기]]`(기존 파서 형식).

### 3-5. 되감기·접기

- **다시 굴리기**: 리수폿 규칙(같은 자리 새 chatId)을 쓰되, 각 항목·계기가 자기 기준 메시지와 인용으로 살아 있음을 판정하므로 chatId가 유지되는 편집·이어쓰기도 맞는다. 사라진 항목은 **지우지 않고 회색 표시**(되살리기 가능). `replaces`로 대체됐던 이전 항목은 대체 항목이 죽으면 자동으로 다시 살아난다.
- **접기**: 변경 기록 800건 초과 시 기준 메시지가 최근 200개 메시지 밖인 것부터 쌍별로 합쳐 접는다. 칸 항목 상한 초과 시 오래된 항목을 코드가 한 줄 요약(모델 없음).
- 저장 크기 추정: 인물 1명 2~4천 자 × 등장 인물 20명 ≈ 4~8만 자 + 기록 800건 × 150자 ≈ 12만 자. **실측 후** 상한 조정.

## 4. 본편에 주기 (리수폿 Router+Director를 코드로)

### 4-1. 인물 고르기 (Router 대체)

지금 로어북 고르기(`pickLore`: 최근 10마디에서 이름·별명 한국어 경계 규칙으로 찾기)가 이미 이 일을 한다. 그 결과를 그대로 쓰고 둘을 더한다: 상태창 동행 칸, 상황판에서 현재 장소에 있는 요원. 최대 6명.

- 리수폿 Router(모델)와의 차이: 대명사·암시만으로 가리킨 인물은 코드가 못 잡는다. 대신 리수폿도 Router 결과에 「이름이 직접 나온 인물」을 코드로 보충한다(`includeMentionedCharacters`). 우리는 그 코드 부분만 있는 셈이다. 차이는 작다.

### 4-2. 무엇을 주나 (Director 대체 — 사실만)

요원 자리 항목(`goei_lore_agent`)에 들어가던 **죽은 시트 대신 살아 있는 기록**을 넣는다(설정: 대체 / 시트 뒤에 덧붙임).

```
## 쟈알디 (living record · updated this chat)
Identity: 관리국 종합대응팀 부장 …
Personality: …
Current state: 왼팔 부상 (3일차, 유저를 감싸다). 의무실 치료 거부.
Knows: 유저가 내통자 명단을 봤다는 것 / 데쥬레가 격리팀으로 옮긴 이유
Does not know: (코드가 「아는 정보」에 없는 이 채팅의 주요 비밀을 나열) 유저의 전직
Relationship → {{user}}: Interest (관심). Seeks shared time, offers reliable help and concern. Expression: very restrained.
Address → {{user}}: '너', informal (since 3일차).
Open threads: 명일 아파트 재조사 약속(미이행) …
Recent: 3일차 명일 아파트 투입, 유저 구조 …
```

- 인물당 400~800자(한국어 ≈ 400~800 tok). 5명이면 2,000~4,000 tok. 시트(인물당 영어 1,000~1,200 tok)를 **대체**하면 본편 입력 순증가는 거의 없다.
- 「Does not know」는 **코드가** 만든다: 이 채팅에서 기록된 비밀·사실 목록 중 이 인물의 `knowledge`에 없는 것. 리수폿 Director의 지식 경계 기능을 가장 싸게 흉내 내는 방법이다. 본편 모델이 어기면 다음 갱신기가 「그 인물이 알게 됨」으로 기록해 버리는 부작용이 있어서, 지침에 「기록상 모르는 인물이 아는 듯 말하면 그 발화는 지식 근거로 쓰지 않음」을 넣는다.
- 숫자·모델 인용은 넣지 않는다. 호감은 단계 이름 + 리수폿 단계 행동 설명 + 표현 정도 꼬리.
- 위치: 기존 요원 자리(삽입 순서 600) 그대로. 상태창 블록·막간은 지금 자리 유지.
- 예산: 로어북 예산(Risu 토큰 예산의 90%) 안에서 인물 수를 줄인다. 기록이 시트보다 작으면 남는 예산은 그대로.

### 4-3. 선택: 짧은 Director (안 ③)

- 켜면 본편 요청 **앞**에 보조 1회: 입력 = 장면 인물 기록(위와 같음) + 직전 2쌍 + 이번 유저 입력. 출력 = 영어 8줄 이하: 각 인물의 이번 턴 반응 방향 1줄, 지키거나 드러내면 안 되는 정보 1~3줄. 리수폿 `director_facts`(사실형)에 가깝게 **연출 제안 금지**.
- 지침 약 1,500 tok + 자료 4,000~8,000 tok. 지연 +5~15초.
- 기본 **끔**. 「인물이 모르는 비밀을 자꾸 말한다」가 실제로 문제가 되는 사용자에게 권한다.

## 5. 필드 게임 연동

- 대사 선택: 호감 단계 → hostile(≤ −1) / 직급 칸(0~60) / 직급 칸 + close 섞기(61~180) / close(181~). `{호칭}` = `address.toUser`(없으면 대사 JSON `address`). 조사 보정 `josa()`.
- 필드 대화 모델 입력에 그 인물의 **살아 있는 기록**(상태·아는 정보·관계·호칭)을 넣는다. 지금 `brain.ts`는 로어북 시트를 넣는데, 같은 자리를 기록으로 바꾼다.
- 필드 행동·대화 태그 → `Change(src: field|fieldtalk)`. 상태 변화(부상·동행)도 `state`·`history` 항목으로 코드가 기록(모델 없음).
- 필드 브랜치 `Relations`(전역 localStorage, −3~+3)는 한 번 가져오기(favor × 30 → manual 계기) 뒤 폐기. **필드 브랜치와 겹치므로 시작 전 확인.**

## 7. 예상 문제

1. **갱신기가 기록을 망가뜨림**(없는 사실 추가, 유효한 항목 삭제): 인용 필수, 항목 단위 교체, `replaces` 이력, 고정, 취소. 삭제는 `remove`도 인용 필수.
2. **본편이 「Does not know」를 어기고 갱신기가 그걸 사실로 기록**: 4-2 지침. 그래도 새면 사용자가 취소.
3. **되먹임**(기록 주입 → 본편이 그대로 묘사 → 갱신기가 새 사실로 중복 기록): 「이미 기록된 항목과 같은 뜻이면 upsert 금지」 + 코드의 유사 문장 검사(정규화 후 80% 일치면 버림).
4. **영어 시트 → 한국어 기록 혼재**: 처음 등장 때 번역 1회(선택) 또는 갱신기가 점차 교체.
5. **채팅 저장 충돌**: 응답 대기 중 보류, 같은 채팅 확인, 덧붙이기만, 큐.
6. **다시 굴리기**: 리수폿과 같은 감지 + 인용 검사. chatId 실측 1회는 그대로 필요.
7. **저장 크기**: 3-5 접기. 실측 후 상한.
8. **비용**: 매 턴 1~1.6만 tok. 보조 모델 속도 제한 시 N턴 모드로 자동 전환 제안.
9. **별명·동명**: 별명 표(위키·연락처·대사 JSON) + 「부장」처럼 겹치는 별명은 구간의 조직 단서로 좁히고 모르면 버림.
10. **미성년**: `minor` 인물은 호감 단계 문장을 「믿고 따름·아낌」으로, 관계 칸에 연애 표현 금지 지침.
11. **필드 브랜치와의 충돌**: `brain.ts` 시트 자리·`Relations`·태그 파서를 건드림 → 합치는 시점 확인.
12. **카드 수정**: 신분 칸만. 요원 자리 항목은 이미 플러그인이 채우므로 카드 수정 없음.

## 8. 시험

| # | 시험 | 기준 |
| --- | --- | --- |
| 0 | chatId 실측(다시 굴리기·스와이프·편집·이어쓰기) | 3-5 규칙 확인 |
| 1 | 시트 → 기록 시작값 변환 | 요원 12명 시트가 칸에 맞게 들어감 |
| 2 | 갱신기 정확도 | 실제 로그 30턴 × 보조 모델 2종, 사람이 정답 표시. 항목 정밀도 80%↑, 잘못된 삭제 0 |
| 3 | 재계산·되감기 | 골든 파일. 응답 교체 시 항목 회색·이전 항목 복귀 |
| 4 | 주입 크기 | 5명일 때 본편 입력 증가 ≤ 시트 대체 전 |
| 5 | 본편 품질 | 같은 장면 20턴: 시트 / 기록 / 기록+Director. 사실 어긋남·비밀 누설 횟수 비교 |
| 6 | 동시 저장·채팅 전환 | 응답 유실 0, 다른 채팅 쓰기 0 |
| 7 | 필드 연동 | `tests/field-harness.mjs`로 단계별 대사 칸·호칭 |
| 8 | 저장 크기·지연 | 20명·800건에서 체감 지연 없음 |

## 9. 만드는 순서

1. 시험 0 + 데이터 구조·재계산 엔진·골든 시험 + 시트→기록 변환 + `relations-base.json`.
2. 갱신기(지침·검사·쓰기 규칙) + 수동 「지금 갱신」 → 시험 2로 정확도 측정.
3. 본편 주입(시트 대체) + 인물 탭 1차.
4. 매 턴 자동 갱신 + 신분 칸.
5. 필드 연동(필드 브랜치와 합칠 때).
6. 측정 뒤: 짧은 Director, 인물끼리 감정, 시트 번역.

---

## 10. 사용자가 정할 것

1. 안 ②(기록 1회 + 코드 주입, Director는 선택)로 갈지, 안 ③을 기본으로 켤지.
2. 본편에 넣을 때 **시트 대체**가 맞는지(시트 뒤 덧붙임은 토큰이 2배).
3. 갱신 기본 **매 턴**이 맞는지.
4. 인물끼리 감정(`npc_emotion`)을 1단계에서 뺄지.
5. 영어 시트를 처음 등장 때 한국어로 번역(인물당 1회)할지.
6. 필드 브랜치 코드(`brain.ts`·`Relations`)를 언제 합칠지.
7. chatId 실측을 직접 해 줄 수 있는지.
