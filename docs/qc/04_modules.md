# QC 04 · 플러그인 창 안 기능 모듈 (2026-10-28)

영역: 괴담넷, 괴담톡, 위키, 상황판(관제실·요원·일지·지도·사진), 가계부, 인물 기록·세력 평판, 이미지 지침 화면, 보조 모델 호출 공통(`host/llm.ts`·`host/joint.ts`·자동 확인).
방법: 가짜 Risu(`tests/browser.mjs` hostScript 복사·확장)에서 실제 번들(`dist/goei-plugin.js` + 본체)을 Chromium 으로 띄우고 `window.__llm` 큐로 모델 응답(정상·깨진 JSON·빈·실패·느림)을 흉내 내 화면을 실제로 조작했다. 엔진 분기는 `node --test` 단위 시험.
(이 작업은 사용량 한도로 멈춘 앞 요원의 일을 이어받았다. 앞 요원의 탐색 스크립트 `tests/_qc_*.mjs` 는 내용을 `tests/qc-modules-*.mjs` 로 정리하고 지웠다.)

시험 파일
- `tests/qc-modules-browser.mjs <fixture.json>` — 20개 절. `ONLY=G1,P4` 처럼 절만 골라 돌린다.
- `tests/qc-modules-perf.mjs <fixture.json>` — 큰 데이터 렌더 시간 (3초 넘으면 실패).
- `tests/qc-modules.test.mjs` — 고친 것들의 회귀 단위 시험 6개 (`npm test` 에 포함).

## ④ 스스로 내린 결정

- 결정: 시험이 채팅 값을 밖에서 바꾼 뒤에는 창을 닫았다 다시 연다(`reopen`). 근거: 창은 열 때 채팅을 읽고 그 뒤로는 자기 조작만 반영한다. Risu 플러그인 창은 채팅 위를 덮어 그동안 채팅이 밖에서 바뀌지 않으므로 버그가 아니다. 앞 요원의 시험이 탭 이동만으로 다시 읽힐 거라 가정해 여러 절이 틀렸던 것을 이렇게 고쳤다.
- 결정: 시험의 `nav` 는 이미 그 탭이면 누르지 않는다. 근거: PC 메뉴에서 보고 있는 탭을 한 번 더 누르면 상황판으로 가는 것은 사용자 결정(2026-10-21)이다.
- 결정: 모바일 절(390×844, 터치) 시험 페이지에 `<meta name="viewport" content="width=device-width">` 를 넣었다. 근거: 없으면 Chromium 이 `isMobile` 페이지를 980px 로 배치해 모바일 CSS(`max-width: 760px`)가 아예 안 걸린다. 실제 Risu 는 이 메타가 있다.
- 결정: 시험 기대값만 틀렸던 것은 동작을 바꾸지 않고 시험을 고쳤다 — 공지 보관 기본 상한 20은 저장 때 적용(원본 값), 건너뛴 답장의 내 말은 남음, 1:1→단톡 승격 때 1:1 기록(내 선물 포함)이 남음, 정답 문단 속 각주도 접힘, 위키 `{{ }}` 는 저장본만 무력화하고 창에는 글자로 보임, 로어북 있는 주제 문서는 「로어북 있는 문서」 칩을 켤 때만 본편에 들어감(v0.16.27 사용자 결정), 인물 갱신의 `m` 꼬리표는 읽는 구간 안 순번(직전 쌍 1 → 새 응답은 m4), 인용은 3글자 이상, 본편 호칭의 `{{user}}` 는 페르소나 이름으로 풀림.
- 결정: 인물 숫자 설정 수정으로 「호감 변화 속도」에 `'0'` 이 저장돼 있으면 이제 기본값 1 대신 최소값 0.25 가 된다. 화면 선택지(0.5~2)로는 0 을 고를 수 없어 실사용 영향은 없다.

## ⑤ 고치지 못했거나 확인이 필요한 것 (보고만)

- `tests/browser.mjs` (영역 밖) 이 141행 「시작 전에도 세계 편집 트리」에서 실패한다: 설정 창이 탭 구조(2026-10-27)로 바뀌어 `ed-node agent` 가 「세계」 탭을 눌러야 보이는데 시험이 옛 구조를 가정한다. 이 영역 수정과 무관하다(편집 창 코드는 건드리지 않았다). 설정 창 담당 영역에서 고칠 것.
- `tests/browser.mjs` 등 기존 모바일 시험(`isMobile: true`)도 viewport 메타가 없어 980px 배치로 돈다. 모바일 레이아웃을 실제로 재지 못하고 있을 수 있다 (영역 밖, 보고만).
- 인물 기록 매 턴 갱신(`requestPeopleUpdate('turn')`)은 응답 이벤트의 채팅 번호가 아니라 「지금 채팅」(`loadContext`)을 읽는다. Risu 에서 응답은 지금 채팅에 오므로 실사용 문제는 아직 못 찾았다. 사용자가 응답 도중 다른 채팅으로 옮기면 그 응답이 다음에 그 채팅을 열 때 읽힌다(읽음 표시 기준이라 빠지지는 않음).
- 실제 Risu·실제 모델로는 돌리지 않았다 (인계서 4-1 「아직 실제 Risu에서 확인 못 한 것」 그대로).
