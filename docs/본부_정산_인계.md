# 본부·정산 검증 인계

기준: `codex/metroidvania-run-system`의 `b674c09f130242f780f444d80c8c5ba78401c90a`.
작업 브랜치: `codex/hq-settlement`. 기존 쟈알디로 검증했으며 캐릭터 자산, engine, stage, 저장 봉투는 수정하지 않았다. 별도 저장 체계도 추가하지 않았다.

## 본부 변경

- 로프 귀환은 임무 미달성이어도 `return`, 메뉴 포기는 `withdraw`, 사망은 `evac`. 본부 임시 시연 어댑터의 미달성 귀환→철수 변환도 제거했다.
- `missionDone`을 성공 증거로 신뢰하지 않는다. 목표 깊이, 중복 제거한 규칙 수, 구조 대상, 진압 대상, 실제 소지 회수물, 시험 성공, 추격 층 클리어를 확인한다. 아파트 조사는 `r_` 규칙만 센다. 노부부는 정규화한 `elder` 완료 기록 또는 `elder_f`와 `elder_m` 양쪽 처치가 필요하다.
- 실제 층의 `sendFound()`는 송신 후 `found`를 비운다. 본부는 현재 출동의 `sent`도 확인한 규칙에 포함한다. 이 문제는 Chromium 로프 귀환에서 성공 미달성으로 재현한 뒤 고쳤다.
- 결과와 `stage.*` 기록의 규칙·구조 기록을 합치고 중복 제거한다. 송신 규칙은 모든 종료 방식에서 보존하며 후송의 미송신 규칙 절반 계산 전에 중복을 제거한다. 가방/보급품은 결과 원본과 참조를 분리한다.
- 결과 runId와 launch runId가 다르면 거부한다. 일치하는 `active`의 임무·요원·seed만 정산하고 active를 소비한다. 마지막 결과 재호출뿐 아니라 다른 출동 정산 뒤 오래된 결과를 재전달해도 보상을 중복 지급하지 않는다. 기존 `goei-hq/1` 구조를 유지한다.
- 본부 mount는 resuming 여부와 관계없이 active를 보존한다. 로딩이 끝나기 전 저장·출동 입력을 막고, 로딩 도중 unmount한 뒤 늦게 도착한 응답을 무시한다. 거부/중복 결과는 정산 창을 열지 않는다.

## 통합 담당 연결 요청

### 1. 체크포인트 stageId 누락 — 이어하기 차단

재현: 본부에서 m1 출동 → 안전 지점 저장 → 새로고침 → 이어하기. `goei-session-journal:0`의 `checkpoint.run.stageId`가 없고 `hq.active`는 남아 있다. `engine/game.ts`의 `resume()`은 stageId로 복원 가능 stage를 찾다가 `지원하지 않는 출동 저장`을 던진다. UI는 `출동 복원 실패`를 표시한다.

`hqAdapter.deploy()`가 넘기는 launch에는 stageId가 없고 `Game.deploy()`는 기본 stage를 선택하면서 그 id를 run에 기록하지 않는다. 신규 출동의 최소 패치 제안:

```diff
--- a/src/game/action/engine/game.ts
+++ b/src/game/action/engine/game.ts
@@
   deploy(run: RunConfigCore, saved?: RunCheckpoint) {
     const stage = this.mods.stages.find((s) => s.id === run.stageId) ?? this.mods.stages[0];
+    run = { ...run, stageId: stage.id };
     this.inHub = false;
```

기존 checkpoint에도 복원 시 호환 처리가 필요하다. 이 기준판의 본부 출동에서 누락된 stageId는 `elevator`였으며, 테스트 입력에 그 값만 채워도 복원이 통과한다. 기존 저장 원문을 버리거나 active를 지우지 말고, 지원 stage 검증 전에 기존 본부 출동만 이관한 복원 입력을 만들고 `deploy()`에도 동일한 입력을 넘길 것. 본부는 `HqHost.resuming` 유무로 active를 삭제하지 않는다.

추가 경계 보존: `hqAdapter.onReturn()`은 현재 결과 runId를 launch runId로 무조건 덮어쓴다. 본부의 불일치 거부가 동작하려면 `runId: (r as RunResult).runId ?? l.runId`처럼 이미 전달된 runId를 보존해야 한다. 현재 `toHqResult`는 runId를 생략하므로 기본값은 그대로 필요하다.

### 2. 회수품 감정 수치 누락

`node tests/hq-integration-probe.mjs` 출력:

```text
inventory: { id: photo, research: 8, value: 40 }
result:    { id: photo, name: 얼굴 없는 사진 }
researchAwarded: 1
```

`itemsLink.tick()`이 `BagEntry`를 `{ id, name }`으로 축소해 본부의 기본 감정치 1이 적용된다. 최소 패치:

```diff
--- a/src/game/action/engine/itemsLink.ts
+++ b/src/game/action/engine/itemsLink.ts
@@
-      w.notes.bag = ir.bag.map((b) => (b ? { id: b.id, name: b.name } : null));
+      w.notes.bag = ir.bag.map((b) => (b ? { ...b } : null));
```

필요한 본부 인터페이스는 기존 `RunResult.bag: { id, name, research?, value? }[]` 그대로다. 마지막 tick 이후 종료하는 경로에서도 최종 인벤토리 snapshot을 전달해야 한다.

### 3. 점검표 회수와 가방 연결

동일 probe, seed 42의 실제 점검표 `onInteract` 후 `outing.items=['checklist']`이지만 `notes.bag`는 빈 6칸, `stage.checklist`도 없다. 현재 m7은 실제 점검표를 가지고 돌아와도 성공할 수 없다.

필요 인터페이스: 실제로 소지한 점검표를 최종 `RunResult.bag`에 `{ id:'checklist', name:'서명란이 빈 점검표', research, value }`로 전달. 습득 시 아이템 모듈의 가방 용량·제거/거래·체크포인트와 함께 처리해야 한다. 단순 `stage.checklist=true` 성공 플래그나 별도 본부 보관소는 만들지 않는다. 최소 연결 지점은 `stage/module.ts`의 checklist 습득과 거래 소비, `itemsLink.ts`의 단일 인벤토리다. 가방이 꽉 찬 실패와 거래 후 사라짐까지 통합 담당이 함께 연결해야 하므로 임의의 자동 지급 패치는 적용하지 않았다.

### 4. 노부부 진압 기록

`createEnemy('elder')`는 실제 `elder_f`를 만들고 짝 `elder_m`을 소환한다. 본부는 한 명만 처치하고 m6 성공 처리하지 않는다. 엔진의 `bossesDown`은 `boss` 표시가 있는 몸만 기록하므로 짝의 처치/완료 의미를 정리해야 한다. stage의 guardian 판정도 문자열 `elder`와 실제 사망 이벤트 `elder_f`/`elder_m`을 직접 비교한다.

필요 인터페이스: 두 명 처치 완료 시 `notes.bosses`에 `elder` 한 번, 또는 두 실제 kind를 모두 보존. 규칙 통과는 적 모듈이 `guardianCleared { kind:'elder', how:'rule' }`을 내보내므로 stage의 guardianSkip/방 완료와 함께 연결해야 한다. 규칙 통과를 진압 임무 성공으로도 인정하려면 그 완료 의미를 본부에 명시적으로 전달할 것. 한 명 처치만 `elder`로 바꾸는 패치는 부정확하다.

다른 담당 소유 파일의 패치는 위 제안만 남겼다. main 병합, 공용 브랜치 덮어쓰기, 릴리스는 수행하지 않았다.
