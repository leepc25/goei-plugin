# 쟈알디 제작 시행착오·PixelLab 실험·비용 추정 검토 보고서

작성일: 2026-10-20 (한국 시간)
목적: Claude가 제작 방식, 실험 결과, 비용 계산 및 다음 제안을 독립적으로 검토하도록 이 대화의 결정과 실패를 정리한다.
상태: 완성 보고가 아니다. 전체 캐릭터와 걷기 모두 최종 승인되지 않았다.

## 1. 먼저 읽어야 할 결론

1. 기존 제작은 동작별 체형 변화, 좌우 팔·다리 대응 오류, 전신 운동 부족을 반복했다. 국소 수정과 재생 속도 조정만으로 해결하지 못했다.
2. 사용자는 128px 정자세 키, 게임 가독성 중심 체형, 동일한 얼굴·몸통·팔다리 치수, 완성된 전신 프레임을 최우선으로 요구한다. 고정 몸통에 사지만 회전시키는 방식은 명시적으로 반려됐다.
3. PixelLab MCP 연결 및 실제 생성·다운로드·게임 적용은 성공했다. 체험 생성량 40 중 4를 사용해 새 걷기 8프레임을 생성했다. 마지막 잔액 조회는 36, 유료 크레딧 $0.00이다.
4. 사용자는 PixelLab 결과가 기존 Codex 제작보다 훨씬 낫다고 평가했다. 그러나 매끄럽지 않다는 지적도 했고 최종 승인하지 않았다.
5. 실제 사용한 기능은 `animate_image` 하나다. 프리셋, 뼈대 기반 생성, PixMiniMax, Pro 편집은 아직 이 캐릭터로 시험하지 않았다.
6. Codex가 제시한 '쟈알디 한 명에 2,500~5,000 생성량, 어렵게 되면 6,000~10,000 이상'은 실측에 근거하지 않은 과도한 추정으로 사용자 지적 후 철회됐다. 승인 예산이나 필요한 최소 사용량으로 재사용하면 안 된다.
7. Artisan 월 $24 플랜을 먼저 권한 것도 성급한 추천으로 철회됐다. 지금 필요한 것은 남은 체험량으로 방식별 합격률과 실제 차감량을 측정하는 일이다.
8. 보고서 작성 중 유료 결제 또는 추가 이미지 생성을 하지 않았다. 사용자에게 요구된 것은 GitHub 보고서 공유이며, Claude에게 직접 메시지를 보내지는 않는다.

## 2. 사용자 요구와 결정의 흐름

### 2.1 로컬·클라우드 통합

- 로컬 작업과 기존 클라우드 작업을 비교·보완해 `goei-plugin` 하나로 통합하는 방향을 선택했다.
- 저장소는 메인 봇을 맡은 Claude와 기존 Codex 작업이 함께 사용한다. 메인 봇 코드에 무관한 변경을 하지 않는다.
- 공용 엔진은 `src/game/action/`이다. 과거 로컬 ARPG는 역사 자료로 보존하며 별도 현행 엔진으로 확대하지 않는다.
- 사용자는 클라우드판의 가독성을 더 좋게 보았다. 제한된 픽셀에서 길쭉한 실사 비율을 고집하지 않기로 했다.
- 128과 256 해상도 비교를 거쳐 원본 정자세 키 128px, 게임 정수 2배 표시를 선택했다. 캐릭터 30명 이상, 적·배경·아이템까지 포함한 저장량과 메모리 부담이 고려됐다.

### 2.2 작화와 전신 동작

- 기본 서기에서 선호했던 비율을 출발점으로 삼되, 최신 결정은 게임 가독성 중심 체형과 128px다.
- 스탠스마다 머리 크기·가슴·골반·팔다리 두께가 달라지면 안 된다.
- 걷기·달리기는 양발 지지 교대, 반대 손발, 골반과 어깨의 반동이 있어야 한다.
- 앉기는 신체 축소가 아니라 관절 굽힘으로 표현한다. 앉아 이동은 양다리의 실제 지지 교대가 보여야 한다.
- 3단 공격은 좌우좌 또는 우좌우. 약약강의 마지막 공격이 가장 강하고 명확해야 한다.
- 타격은 발끝 추진, 골반·허리 회전, 어깨와 상체의 전진이 연결되어야 한다.
- 기본 대기는 자연스러운 호흡, 전투 대기는 전신의 작은 체중 이동. 과도한 팔 벌림이나 머리만 움직이는 표현은 부적합하다.
- 음식, 병·캔·컵 음료, 붕대·경구약·소독·주입기·타인 치료 등을 구별한다.
- 근접 공격과 원거리 공격 입력은 별도다. 키 바인딩 재설계 자체는 후순위다.

### 2.3 전달 방식과 진행 중단 문제

사용자는 설명·계획만 남기고 작업이 멈추는 패턴에 반복적으로 항의했다. '했습니다', '계속하겠습니다'라는 표현과 실제 구현·검증·전달 상태가 맞지 않았던 것이 별도 실패다. 그림이나 영상만이 아니라 실제 플레이 HTML에 반영해야 한다.

전체 제작이 계속 실패하자 걷기 → 달리기 → 앉기 → 공격 → 나머지 순으로 범위를 줄여 검증하는 방향을 받아들였다. 범위를 줄이는 것은 원인 분리에 도움이 되지만, 생성 방식 자체의 문제를 자동 해결하지는 않는다.

| 체형 | 전투 진입 시 몸이 두꺼워짐, 동작별 머리 크기 차이 | 동일 인체 치수를 강제하는 구조 없이 별도 자세 그림을 생성·보정 |

| 달리기 | 하체가 짧아짐, 한 팔이 고정되고 전완만 움직임 | 부위 단위 수정과 전체 운동의 분리 |

| 쓰러짐 | 제자리에서 풀썩 주저앉음 | 넉백·비행·충돌 등 액션 게임 반응과의 연결 부족 |
| 전달 | 기능 없는 부분 시연, 완료 표현과 실제 상태 불일치 | 기능 시험과 시각 품질을 혼동하고 완료 조건을 느슨하게 적용 |

판단: 일반 이미지 생성은 외형 참조와 프롬프트를 주어도 프레임 간 해부학·팔다리 대응·시간 연속성을 반드시 보장하지 않는다. 잘못 그린 동작은 속도 변경으로 고칠 수 없다. 다만 'AI로 이 작업은 불가능하다'는 결론까지 검증된 것은 아니다.

### 3.1 기존 파일에 남은 실패 증거

- `game-src/action/production-v5/animation-review.json`: 걷기·달리기·앉기·공격·섭취 시트의 미승인 사유.
- `walk-guided-source.png`: 보행 자세 가이드를 함께 사용했으나 팔 대응과 몸통 통일성 미해결.
- `run-crouch-source.png`: 반대 착지에서 팔 배치 반복, 앉기 지지 교대 불명확.
- `melee-source.png`: 스트레이트와 훅에서 같은 팔이 반복되어 최종 연계로 반려.
- `melee-revised-source.png`: 몸통 회전 수정 후에도 손 순서와 기준표 대비 체격은 미검증.
- `consumption-source.png`: 전신과 소품 동작은 있으나 다른 시트와 통일성 미승인.
- `game-src/action/walk-study/review.json`: 초기 걷기 연구판의 미승인 기록. 이 JSON은 r01 기준이며 이후 r02와 혼동하면 안 된다.
- r02 로컬 패킹 결과 높이: 128,127,128,127,123,124,124,126px. 한 배율로 처리했지만 자세 차이와 인체 크기 오류를 구분해 재검토해야 한다.

## 4. 구현 기능과 작화 완성은 별개

공용 시뮬레이션에는 근접/원거리 분리, 탄약·재장전, 잡기·잡기 타격·던지기, 시간 이벤트 기반 섭취·치료 로직 등이 들어간 기록이 있다. 이전 기록상 시뮬레이션 시험 22개와 타입 검사를 통과했다.

그러나 이것은 해당 행동의 최종 전신 작화가 존재한다거나 현재 시연판이 전체 게임 완성본이라는 뜻이 아니다. 이번 보고서 작성에서 이전 시험 22개를 모두 재실행한 것은 아니며, 과거 기록과 현재 확인 결과를 구분한다.

전체 행동 범위와 검수 기준은 [제작 기준서](JYALDI_PRODUCTION_STANDARD.md)를 우선한다. 생활·전투 구분, 타인 치료·잡힌 상대 반응 등은 범위에서 조용히 제외하면 안 된다.

## 5. 외부 프로그램 검토 과정

### 5.1 Blender / Mixamo / Aseprite 제안

- Blender: 같은 신체 모델을 유지하며 전신 동작을 만들고 2D 전신 스프라이트로 출력하는 방식.
- Mixamo: 걷기·달리기 등 모션 프리셋을 가져와 모델에 적용하는 방식.
- Aseprite: 픽셀·윤곽·프레임을 정밀 편집하는 후처리 도구.
- 장점으로 예상한 것은 신체 구조의 고정과 모션 재활용이다. 단, 모델 외형 재현, 동작 보정, 128px 도트 마감이 필요하고 자동 완성이 아니다.
- 사용자 요구는 도구를 자신이 배우는 것이 아니라 Codex가 사용해야 한다는 것이다.
- 실제 Blender 설치/모델링, Mixamo 로그인/다운로드, Aseprite 작업은 하지 않았다. 이 경로는 검증 완료된 대안이 아니다.

사용자가 '기준 이미지를 넣으면 동작 이미지를 만드는 프로그램'을 다시 지적한 뒤 PixelLab과 Ludo.ai가 후보로 조사됐다. 초기 안내가 3D 제작에 지나치게 치우쳤다는 점을 Codex가 인정했다. Ludo.ai는 문서 조사만 했고 계정 연결·생성 시험은 하지 않았다.

### 5.2 PixelLab 연결 시행착오

1. 브라우저 자동 조작으로 PixelLab 접속을 두 번 시도했으나 도구 프로세스가 시작 단계에서 종료됐다. PixelLab 로그인 거부로 확인된 것은 아니다.
2. 앱에서 웹페이지를 여는 요청은 가능했으나 실제 로그인 화면을 조작하는 데 성공하지 못했다.
3. API 연결을 대안으로 제안했다. 사용자가 계정의 Secret을 확인했다. Secret은 인증 토큰이며 보고서·시연판·저장소에 포함하지 않는다.
4. 비밀 입력 창과 Windows 사용자 암호화 저장을 준비하는 PowerShell 실행이 백신에 의해 차단됐다. 차단을 우회하지 않았고 해당 시도로 인증·생성을 하지 않았다.
5. Codex가 현재 Windows 앱 화면을 확인하지 않고 MCP 메뉴 위치를 안내해 혼란을 일으켰다. Hooks는 MCP 연결과 다른 기능이다.
6. 사용자가 로컬 Codex `config.toml`에 PixelLab HTTP MCP 주소와 인증 헤더를 설정하고 앱을 완전 종료·재실행했다.
7. 재실행 후 PixelLab 도구가 노출됐으며 `get_balance` 성공으로 실제 계정 인증을 확인했다.

설정값 중 공개 가능한 서버 주소는 `https://api.pixellab.ai/mcp`다. 개인 설정 파일과 인증 헤더 값은 이 보고서에 포함하지 않는다. 도구 목록이 보인다는 사실과 실제 계정 요청 성공은 따로 확인했다.

## 7. 실제 PixelLab 걷기 시험

### 7.1 입력·생성 조건

| 항목 | 값 |
|---|---|

### 7.2 게임 적용

- 시연판: [PixelLab 걷기 시연 HTML](../release/demo/jyaldi-pixellab-trial.html). GitHub 파일 보기만으로 실행되는 것은 아니며 다운로드 후 브라우저로 열어야 한다.
- 전신 프레임을 160×160 그대로 패킹했다. 프레임별 확대·축소 또는 신체 부위 재조립 없음.
- 공통 anchor (80,144), 표시 배율 2, 정자세 키 128px.
- 1~8 생성 프레임을 같은 시간 간격으로 반복한다. 입력 정자세는 정지에 사용한다.
- 이동 거리에 따라 주기를 진행시키며 현재 한 주기 기준 거리는 게임 좌표 200이다. 보폭을 측정해 접지에 맞춘 결과가 아니라 임시 조정값이다.
- 출발·정지 전용 작화는 없다. 실제 보행 속도와 접지 속도 동기화가 검증된 상태도 아니다.

### 7.3 검수 결과

사용자 평가: '네가 만든 것보다 훨씬 낫긴 하다', 그러나 움직임이 매끄럽지 않다는 지적.

관찰한 미해결 사항:

- 걷는 도중 몸통이 정면 쪽으로 돌아가 고정 시점 요구를 지키지 못했다.
- 마지막 생성 자세가 첫 생성 자세와 자연스럽게 연결되지 않는다.
- 팔 스윙과 좌우 손발 교대가 충분히 명확한지는 추가 검토 필요.
- 발 위치가 프레임별로 변한다. 자연스러운 발 들림·몸통 bob인지 접지 오류인지 구분하지 않고 자동 정렬하면 안 된다.
- 기준 그림에서 걷기, 걷기에서 정지로 넘어가는 전환 작화가 없다.

입력+8 생성 프레임의 alpha bounding box (left,top,right,bottom):

```text
(54,16,105,144), (54,19,103,145), (56,17,99,144),
(58,15,94,143), (62,14,93,142), (62,15,94,141),
(59,17,96,142), (59,18,94,145), (58,16,96,145)
```

높이만 비슷하다고 머리·팔다리의 실제 치수가 일치한다는 증거는 아니다.

실행 검증: 방향키 이동, 정지 후 neutral 복귀, 1~8 전체 프레임 도달, 프레임 선택, 속도 변경, 일시정지, 모바일 가로 overflow 없음, 브라우저 오류 없음. 타입 검사도 통과했다. `visualApproval: false`이며 기능 시험은 시각 합격 판정이 아니다.

### 7.4 원인에 대한 책임 구분

- Codex 요청·적용 문제: 자연스러운 반복을 요구했지만 마지막 이미지 지정은 사용하지 않음; 생성 후 보행 단계별 타이밍과 이동 속도를 분석하지 않고 균등 재생; 출발/정지 전용 작화 없음.
- 생성 결과 문제: 시점 회전과 반복 자세 불일치. 재생 속도만 바꾸면 해결된다고 말할 수 없음.
- 미검증: 같은 시작/끝 이미지를 지정하면 문제를 해결한다는 보장은 없음. 정자세를 양끝에 넣으면 오히려 매 주기 멈춤이 생길 수 있어, 순환 보행용 접촉 자세와 전환용 정자세를 구분해야 함.
- 결론: 도구가 전부 잘못했거나 프롬프트만 잘 쓰면 완성된다는 양극단 모두 근거 부족. 다음 시험은 하나의 변수씩 비교해야 함.

## 8. 비용 단위와 크기 계산

### 8.1 서로 다른 단위

- generation: 구독/체험 차감량. 이미지 1장, 호출 1번, 대화 토큰과 동일하지 않다.
- frame: 애니메이션 그림 한 장. 1회 호출로 여러 프레임을 받을 수 있다.
- USD credits: 별도 달러 잔액. 월 제공 생성량을 같은 숫자의 현금 크레딧으로 해석하면 안 된다.
- 게임 표시 배율: 128px를 2배 표시하는 것은 생성 비용을 늘리지 않는다.
- 캐릭터 키와 캔버스 크기: 이번 캐릭터 키는 128px지만 여백 포함 캔버스는 160×160이었다. 투명 여백도 픽셀 예산에 포함된다.

### 8.2 Text v3의 산술 예시

공식 표와 연결된 v3 도구 설명에 맞춘 계산은 `ceil(width × height × generated_frames / 65536)`이다. 이번 실측은 `ceil(160×160×8/65536)=4`와 일치한다. 이 식을 모든 모델에 일반화하지 않는다. 생성 총 픽셀 상한은 524288이며 프레임 수 등 개별 제한도 적용된다.

| 캔버스 | 8프레임 계산량 | 16프레임 계산량 |
|---|---:|---:|
| 64×64 | 1 | 1 |
| 96×96 | 2 | 3 |
| 128×128 | 2 | 4 |
| 128×160 | 3 | 5 |
| 144×160 | 3 | 6 |
| 160×160 | 4 | 7 |
| 176×176 | 4 | 8 |
| 192×160 | 4 | 상한 초과 |
| 192×192 | 5 | 상한 초과 |
| 256×256 | 8 | 상한 초과 |

160×160/8 외의 수치는 이번 계정으로 실측한 것이 아니다. 특히 직사각형 크기 지원·실제 과금은 요청 전 확인한다. 등록 캐릭터 v3 경로는 실루엣에 따라 생성 캔버스가 커져 예상보다 차감될 수 있다는 도구 안내가 있다.

### 8.3 다른 도구의 안내

- 뼈대 v3: 안내상 3프레임 2, 8프레임 3, 15프레임 4. 출력 최대 256px, 3~15프레임. 쟈알디 실측 아님.
- 프리셋: 방향당 기본량과 큰 캔버스의 분할 배치에 따라 증가. '프리셋이면 무조건 1' 아님.
- PixMiniMax: 다른 과금 방식이며 4~40프레임. 공개 웹 문서와 MCP 설명에서 해상도·플랜 접근 설명 차이가 있어 실제 receipt와 최신 안내를 확인해야 한다.
- 일반 Pro 생성·편집: 안내상 호출당 10~25. 작은 프레임은 묶어 처리 가능하나 일반 edit_image는 큰 프레임에서 한 장 제한이 있다.
- 일반 edit_image의 한도를 전용 animation-edit 또는 outfit-transfer에 그대로 적용하면 안 된다. 각각 다른 한도다.
- 직접 픽셀 편집·타이밍 수정·패킹·게임 통합은 AI 재생성 호출과 분리한다. 무료 직접 편집이 가능하다고 좋은 작화를 자동 보장하는 것은 아니다.

### 8.4 캔버스 제안의 상태

기존 제안: 정자세 키 128 유지, 기본 128×160 또는 144×160, 넓은 공격 192×160, 수직으로 큰 동작에 192×192 이상. 모두 검토 제안이며 새 확정 규격이 아니다.

중요: 비용을 줄이려 캐릭터 자체를 작게 그리거나 팔다리를 프레임에 우겨 넣지 않는다. 동작별 캔버스 여백이 달라도 본체 치수와 바닥 기준은 같아야 한다. 고정 해상도 기준과 패킹 최적화는 양립한다.

2026-10-20 확인한 공식 공개 가격표:

| 플랜 | 월 정가 | 월 생성량 | 전량 사용 시 1000당 비용 | 차이 |
|---|---:|---:|---:|---|

개별 애니메이션 도구의 256px 등 상한은 상위 플랜의 일반 이미지 크기와 별개다. 더 비싼 플랜이 동일 모델의 결과 품질을 자동 개선한다는 근거는 없다. 최종 원화 청구액은 세금·환율·결제 조건에 따라 다르며 여기서는 환산하지 않았다.

PixelLab의 `search_help` 응답에서 받은 추가 정보(결제 화면으로 직접 검증하지 않은 안내):

- 월 생성량을 웹/API/MCP/확장 도구가 공유하며, 구독 생성량을 먼저 차감하고 이후 별도 USD credits를 사용.
- 월 미사용 생성량은 갱신 시 초기화되어 이월되지 않고, 구매한 USD credits는 만료 없이 이월된다고 답변.
- 연간 Apprentice $99, Artisan $220, Architect $500으로 답변.
- 최소 충전액은 찾지 못했다고 답변.
- Apprentice 지속 구독 할인 $12→$10→$9.5→$9을 안내. 공개 홈페이지에는 Artisan $24→$23→$22.5→$22도 있으나 도움말 응답은 이를 확인하지 못했다. 최신 결제 화면에서 재확인할 항목이다.

공식 도움말 자체가 검색 기반 답변이며 확정 계약서가 아니다. 연간 금액, 크레딧 유효기간, 갱신·해지·업그레이드 조건은 구매 전에 실제 계정 화면/약관에서 최종 확인한다. 이 보고서는 구독이나 충전 실행 승인이 아니다.

## 10. 비용 추정 오류와 철회 기록

### 10.1 최초 단순 예시

공식 USD API 예상 단가 $0.0424(128×128,16프레임)를 이용해 30명×30동작×5시도=$190.80이라는 예시를 들었다. 이는 특정 경로 호출만의 산술 예시이며 구독 생성량, 전체 편집 비용, 실제 합격률을 반영하지 않은 값이다. 쟈알디 완성 견적 또는 프로젝트 총비용으로 인용하면 안 된다.

### 10.2 과도했던 전체 예산

Codex는 90~120묶음, 대표값 100묶음으로 잡고 다음 표를 제시했다.

| 당시 가정 | 제시량 |
|---|---:|
| 기준 작화 | 100~250 |
| 100묶음×평균4×3~6회 시도 | 1200~2400 |
| Pro·통일성 수정 | 400~1200 |
| 소품·효과·컷인 | 100~300 |
| 추가 예비 수정 | 300~850 |
| 산술 합계 | 2100~5000 |

여기서 '실무상 2500~5000 권장, 어려우면 6000~10000 이상' 및 Artisan 추천으로 이어졌다.

### 10.3 사용자 반박과 인정한 오류

사용자: 한 명 제작에 월 한도 5000에 가까운 양이 필요하다는 것이 이상하며 착오가 아니냐고 지적.

Codex가 인정한 문제:

- 전 동작 평균 3~6회 시도는 실측 합격률이 아니라 임의 가정이었다.
- 100묶음도 공용 자세·준비/행동/복귀 결합 여부를 먼저 산정하지 않은 수였다.
- 재시도를 이미 계산한 뒤 고가 수정과 예비비를 중첩해 더했다.
- 필수 작업과 선택적 고급 작업을 구분하지 않은 채 총량으로 제시했다.
- 결과적으로 사용자에게 한 명에 반드시 수천이 필요하다는 잘못된 인상을 주었다.

따라서 최초 예산과 그에 기댄 플랜 추천은 철회한다. 고가 편집을 많이 쓰면 그만큼 소비될 수 있다는 가능성과 실제 필요한 비용은 다르다.

### 10.4 현재 유효한 설명

이번과 같은 8프레임/4생성량 방식으로만 계산한 예시:

| 호출 수 가정 | 생성량 | 새 프레임 수 |
|---|---:|---:|
| 50묶음, 각1회 | 200 | 400 |
| 100묶음, 각1회 | 400 | 800 |
| 100묶음, 각2회 | 800 | 1600 (선택되지 않은 후보 포함) |

이것 역시 확정 견적이 아니다. 첫 제작은 수백 단위일 수 있지만 완성까지의 양은 합격률·필요 묶음 수·수정 방식이 결정한다. 생성 프레임 수와 최종 고유 프레임 수를 혼동하지 않는다.

현재 단 하나의 실측은 '160×160 걷기 8프레임 1회 = 4, 품질 부분 개선, 최종 미승인'이다. 재시도 횟수 평균을 추정할 표본 수가 없다.

## 11. 다음 실험 및 비용 관리 제안 (아직 미실행)

1. 먼저 제작 기준서의 행동을 실제 고유 전신 클립, 기존 클립 재사용, 소품만 교체, 엔진 이벤트로 나눈다. 몸통 고정식 재사용은 금지한다.
2. 동일 기준 그림·방향·표시 배율로 걷기를 template / skeleton-v3 / 다른 모델 중 가능한 방식과 비교한다. 등록 캐릭터 생성이 필요한 경우 선행 비용도 기록한다.
3. 각 호출마다 입력·모델·프레임 수·캔버스·예상/실제 차감량·실패 여부·사용 가능한 프레임·시각 결함을 기록한다.
4. 생성 자체 오류와 반복·타이밍·이동 속도 문제를 분리한다. 속도 조정으로 해결할 수 있는 문제에 유료 생성량을 쓰지 않는다.
5. 걷기·달리기·앉기·3단 공격의 대표 시험에서 합격률을 얻은 뒤 양산 범위를 정한다. 한 가지 동작의 합격률을 모든 생활·전투 동작에 그대로 적용하지 않는다.
6. 비용식은 `초기 기준작화 + Σ(동작별 실제 시도량×호출 차감량) + 별도 수정 호출 + 필수 소품/효과`로 관리한다. 이미 포함한 재시도 비용을 예비비에 중복 계산하지 않는다.
7. 남은 체험량은 마지막 확인 36이다. 사용자가 '남은 양으로 무엇을 할 수 있는가'라고 물은 것은 질문이며, 전부 무조건 소모하라는 별도 지시로 해석하지 않는다.
8. 결제 전 추천은 유보한다. Apprentice 2000으로 충분할 가능성이 있으나 아직 보장할 수 없다. Artisan은 실제 월 제작량이 2000을 넘거나 동시 작업 이점이 필요할 때 비교한다. Architect·연간 결제는 현재 근거가 부족하다.
9. 실행 가능한 HTML로 결과를 보여주고, 시각 승인을 기능 테스트 결과로 대체하지 않는다.

## 12. Claude에게 요청하는 검토 항목

- 기존 전체 행동 범위에서 공용화 가능한 전신 클립을 구분해 과도한 '동작 수' 가정을 바로잡아 달라.
- 반복 보행의 첫/끝 접촉 자세, 실제 발의 이동량과 게임 속도, 시점 변화 문제를 시연판과 프레임으로 검토해 달라.
- 프리셋/뼈대 방식이 텍스트 생성보다 적합한지 판단하되 실제 미시험 기능을 성공한 것처럼 전제하지 말아 달라.
- 128px 본체를 유지하면서 캔버스 여백과 비용을 줄일 수 있는지 검토해 달라. 가격 때문에 신체 비율을 바꾸지 말아 달라.
- Pro 수정이 꼭 필요한 부분과 무료 직접 수정·재생 조정으로 가능한 부분을 나눠 달라.
- generation, USD credits, 호출 수, 프레임 수를 분리해 예산을 재산정해 달라. 철회된 수천 단위 견적을 전제로 삼지 말아 달라.
- 도구 안내와 웹 가격표가 다른 부분은 계정·결제 화면 또는 최신 문서로 재확인해 달라.
- 최종 판단은 '가능/불가능' 단정 대신 검증된 것·실패한 것·다음 실험으로 나눠 달라.
