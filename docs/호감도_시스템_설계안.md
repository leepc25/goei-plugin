## 0. 한눈에 보기

**추천: 「장부 + 코드 판정」 공통 바닥 위에 변화 감지를 여러 방식으로 끼우는 하이브리드(안 F).**

- 관계값은 **사건 장부**에서 계산한다. 사건 하나하나에 출처(필드·본편·수동)와 기준 메시지가 붙어 있어서, 다시 굴리기나 삭제를 해도 값이 자동으로 맞는다.
- 숫자는 **언제나 코드가 정한다.** 모델은 「무슨 일이 있었나(계기)」만 고른다(리수폿·기존 필드 설계와 같은 원칙).
- 변화를 알아내는 길은 다섯 가지이고, 사용자가 메뉴에서 고른다.
  1. 필드 안 행동(선물·구해 줌·폭력 등): 코드가 바로 판정, **모델 0회**
  2. 필드 NPC 대화: 이미 부르는 필드 대화 모델이 계기 태그를 같이 냄, **추가 호출 0회**
  3. 본편 이야기: **보조 모델이 몰아서 읽기** (N턴마다 또는 게임 열 때, 뒤에서)
  4. 본편 이야기: 괴담톡·괴담넷 자동이 켜져 있으면 **그 호출에 얹기** (추가 호출 0회)
  5. 본편 이야기: 사용자가 「지금 관계 갱신」을 누를 때
- 본편 모델에게 매 턴 관계 태그를 쓰게 하는 안(안 B)은 **기본으로 쓰지 않는다**(사용자 우려: 본문 품질 저하·다른 태그 오염). 실험용 선택지로만 남긴다.
- 유저 직급은 이미 정한 대로 **상태창(환경 태그)에 한 칸**을 더한다. 관계 판정과는 별개다.

## 1. 지금 있는 것 (설계의 출발점)

| 있는 것 | 위치 | 이 설계에서 쓰는 법 |
| --- | --- | --- |

| 상태창 8칸 | `src/core/world/status.ts` `[▣|날짜|시각|날씨|기온|위치|목표|동행|투입]` | 9번째 칸 「신분」 추가(6장) |

## 2. 공통 바닥: 데이터 구조

어떤 안을 고르든 이 부분은 같다.

### 2-1. 관계의 축

| 축 | 범위 | 뜻 | 움직이는 속도 | 대사·프롬프트에 쓰임 |
| --- | --- | --- | --- | --- |
| 호감 `aff` | −100 ~ 100 | 개인적으로 좋고 싫음 | 느림 | 대사 칸(close/peer/hostile), 단계 문장 |
| 신뢰 `trust` | 0 ~ 100 | 믿고 맡길 수 있는가 | 아주 느림, 배신이면 급락 | 부탁 수락, 정보 공개, 동행 |
| 기분 `mood` | 평온·기쁨·화남·슬픔·불안·피곤 | 방금 일 | 몇 시간이면 평온 | 필드 말풍선 말투 |
| 경계 `guard` | 0 ~ 3 | 지금 위협을 느끼나 | 몇 시간이면 풀림 | 필드 반응(경고·도망) |

- 호감·신뢰는 **본편과 필드 공통, 채팅에 저장**. 기분·경계는 **필드 전용, 저장하지 않거나 짧게만**.
- 범위는 기존 `fieldrel.ts`(−100~100)를 따른다. 리수폿의 −100~300보다 단순하고, 표시 7단계가 이미 있다.
- **취향(첫인상) 축은 넣지 않는다.** 리수폿에는 있지만 우리 대사·필드에 쓸 곳이 없고 판정 비용만 는다.
- **방향이 있다.** `쟈알디 → 유저`와 `유저 → 쟈알디`는 다르다. **유저의 감정은 기록하지 않는다**(리수폿 원칙과 같음. 유저가 직접 연기하므로).

### 2-2. 단계와 대사 칸 연결

| 호감 | 표시 단계 (fieldrel) | 대사 `chars`/관계 칸 | 본편 문장 예 |
| --- | --- | --- | --- |
| −100 ~ −71 | 매우 싫음 | hostile | 「쟈알디는 너를 강하게 적대한다. 필요한 말만 하고 등을 보이지 않는다」 |
| −70 ~ −36 | 싫음 | hostile | |
| −35 ~ −11 | 불편 | hostile(가벼운 쪽) | |
| −10 ~ 10 | 보통 | 직급 칸 그대로(boss/peer/junior/outsider) | (넣지 않음) |
| 11 ~ 40 | 호의 | 직급 칸 + 친한 대사 섞기 | |
| 41 ~ 70 | 친근 | close | |
| 71 ~ 100 | 매우 친근 | close | |

- **상하 관계는 호감과 따로 계산한다**(직급 사다리). 호감은 그 위에 「친함·적대」만 덧씌운다. 상관이 친해도 상관 말투는 유지된다(리수폿 「높은 호감이 반말을 허락하지 않는다」).
- 대사 선택 순서: `special[이름]` 칸 → 호감 단계가 hostile/close면 그 칸 → 아니면 직급 칸. 자세한 건 9장.

### 2-3. 초기값: 미리 만든 표 (실행 중 비용 0)

`game-src/dialogue/relations-base.json` (새 파일, 데이터만)

```json
{
  "version": 1,
  "pairs": {
    "스팡달>데쥬레": { "aff": 40, "trust": 30, "note": "괴롭히지만 챙김 (위키 「스팡달」 관계)" },
    "잼트리>스팡달": { "aff": 50, "trust": 60 }
  },
  "persona": {
    "A00": { "aff": 10, "trust": 20 },
    "B00": { "aff": -30, "trust": 0 },
    "C00": { "aff": -20, "trust": 0 },
    "D00": { "aff": 0, "trust": 10 },
    "E00": { "aff": 0, "trust": 10 }
  },
  "temper": {
    "쟈알디": { "open": 0.6, "grudge": 1.0 },
    "데쥬레": { "open": 1.3, "grudge": 0.8, "gift": 1.5 }
  }
}
```

- `pairs`: 인물 → 인물. 위키에 드러난 사이만 적는다(대사 JSON의 `relations`와 같은 근거). 없으면 0.
- `persona`: 유저의 소속별 출발값. 인물별 예외를 둘 수 있다(`"persona.쟈알디.A00"`).
- `temper`: 성격 계수(기존 설계 6-2). `open` = 호감이 오르는 배율, `grudge` = 내려가는 배율. 위키 성격 근거로 미리 만든다.
- **리수폿의 초기값 규칙을 그대로 쓴다**: 「상사·동료」 같은 이름표만으로 높이지 않는다. 근거가 없으면 0.
- 만드는 법: 개발할 때 Claude가 위키를 읽어 표를 만들고 사용자가 검수한다. 52명이면 실제로 적히는 쌍은 100~200개쯤이다.

### 2-4. 사건 장부 (event sourcing)

관계값을 직접 고쳐 저장하지 않는다. **사건을 쌓고, 값은 매번 계산한다.**

```ts
// 채팅 변수 goeiRelV1
interface RelStore {
  schema: 1;
  baseVersion: number;            // relations-base.json 버전. 표가 바뀌면 다시 계산
  events: RelEvent[];             // 최대 600건, 넘으면 접기(2-6)
  folded: Record<string, Partial<RelValue>>; // 접힌 옛 사건의 합
  pins: Record<string, Partial<RelValue>>;   // 사용자가 고정한 값 (자동 변화 무시)
  scan: { lastIndex: number; lastChatId: string; at: string };  // 본편 몰아 읽기를 어디까지 했나
  persona: { faction: string; rank: string; level: number | null; from: 'status' | 'manual' | 'default' };
}
interface RelEvent {
  id: string;                     // 해시(출처+기준 메시지+쌍+계기)
  src: 'field' | 'fieldtalk' | 'story' | 'manual';
  anchor: string;                 // 이 일이 일어난 본편 메시지 chatId (필드는 그때 본편 마지막 메시지)
  anchorIndex: number;            // 참고용 메시지 번호
  from: string;                   // 감정을 가진 쪽 (인물 이름)
  to: string;                     // '@user' 또는 인물 이름
  cue: Cue;                       // 계기 (2-5 표)
  reason: string;                 // 한국어 한 줄
  quote?: string;                 // 본편 원문 인용 (story만, 검증용)
  delta: { aff: number; trust: number };  // 코드가 계산해 넣은 실제 변화
  at: number;                     // 게임 분 또는 시각
}
interface RelValue { aff: number; trust: number }
```

- **현재값 = 초기값 + 접힌 합 + 살아 있는 사건의 delta 합 → 상한으로 자름.** 고정(pin)이 있으면 그 값.
- **살아 있는 사건** = 기준 메시지(`anchor`)가 지금 채팅에 있는 사건. 다시 굴리기로 그 응답이 바뀌거나 지워지면 사건이 자동으로 빠진다. 기존 필드 장부 설계(8-1 `anchor`)와 같다.
  - 다시 굴리기는 같은 자리에 새 응답이 생기는 것이라 chatId가 바뀐다 → 옛 사건은 빠지고, 새 응답을 다시 읽으면 새 사건이 생긴다.
- 사건은 **사람이 읽을 수 있는 기록**이라 메뉴에서 근거를 보여 주고 되돌리기가 쉽다(7장).

### 2-5. 계기 표 (모델은 이 중에서만 고른다)

기존 `fieldrel.ts`의 표를 넓힌다. 리수폿의 변화량 표(+1/+3/+5/+10/−2/−4/−5/−10/−50)를 계기 이름으로 바꾼 것이다. **이름으로 고르게 하면 모델이 숫자를 부풀리지 못한다.**

| 계기 `cue` | 뜻 (판정 기준) | 호감 | 신뢰 | 큰 사건 |
| --- | --- | ---: | ---: | :---: |
| 작은친절 | 실제로 전해지고 받아들여진 작은 배려 | +2 | 0 | |
| 도움 | 의미 있는 도움, 일을 대신 맡아 줌 | +4 | +2 | |
| 약속지킴 | 서로 아는 약속을 지킴 | +3 | +6 | |
| 선물 | 받는 사람이 반긴 선물 | +4 | +1 | |
| 대가치른도움 | 자기 손해·위험을 감수한 도움, 관계 회복 | +8 | +5 | ○ |
| 구함 | 목숨을 구함, 희생 | +12 | +10 | ○ |
| 비밀공유 | 비밀·약점을 털어놓고 받아들여짐 | +5 | +8 | |
| 실망 | 작은 실망, 무시당함 | −2 | 0 | |
| 무례 | 분명한 무시·모욕, 믿음에 금 | −5 | −3 | |
| 방해 | 일을 망침, 가로막음 | −3 | −2 | |
| 위협 | 위협함 | −6 | −5 | |
| 배신 | 의미 있는 배신·굴욕 | −15 | −40 | ○ |
| 폭력 | 실제로 해침 | −20 | −15 | ○ |
| 중대한위반 | 설정상 용서받기 어려운 일(동료 살해 등) | −50 | −60 | ○ |

- **점수가 없는 것**(리수폿 규칙 그대로): 인사, 외모, 직위, 일상 업무, 아직 답을 못 받은 제안, 이미 반영한 사건, 요약·회상에 다시 나온 사건, 정중한 거절.
- 필드 행동(선물·폭력·구함 등)은 게임 코드가 같은 계기 이름으로 사건을 만든다.

### 2-6. 판정 엔진 (코드, 결정적)

`src/core/relation/engine.ts` (새 파일, 기존 `fieldrel.ts`를 옮겨 넓힘)

```
입력: 계기 목록(쌍별), 현재값, 성격 계수, 같은 날 이미 오른 양, 최근 계기
1. 계기 → 기본 변화량 (2-5 표)
2. 성격 계수: 오르면 × open, 내리면 × grudge, 선물이면 × gift
3. 체감: 최근(같은 게임일 또는 최근 10턴)에 같은 계기가 n번 있었으면 × 1/(1+n)
4. 한 번 판정(한 턴/한 대화)의 쌍별 합: 큰 사건이 없으면 −10 ~ +10으로 자름
5. 하루 상한: 호감 +15 (큰 사건은 예외)
6. 범위: 호감 −100~100, 신뢰 0~100
7. 결과 delta를 사건에 적어 저장
```

- 같은 사건이 두 번 들어오지 않게 `id`(출처+기준 메시지+쌍+계기 해시)로 막는다. 몰아 읽기 구간이 겹쳐도 안전하다.
- **접기**: 사건이 600건을 넘으면, 기준 메시지가 오래된(최근 200개 메시지 밖) 사건부터 쌍별로 합쳐 `folded`에 더하고 지운다. 접힌 사건은 다시 굴리기로 되돌릴 수 없다(오래된 메시지라 실제로 바뀔 일이 거의 없다).
- **시간 감쇠**: 기존 `decay()`처럼 호감은 하루에 1씩 0쪽으로. 기본값 **끔**(본편은 몇 달이 몇 턴에 지나가기도 해서 어색할 수 있다). 메뉴에서 켬.

## 3. 변화 감지: 여섯 가지 안

본편 이야기 속에서 관계가 바뀐 것을 **누가, 언제, 어떻게** 알아내느냐가 핵심 차이다. 필드 안 변화(행동·필드 대화)는 모든 안에서 같다(3-0).

### 3-0. 필드 안 변화 (모든 안 공통)

| 일 | 누가 판정 | 모델 호출 |
| --- | --- | --- |
| 선물·거래·구해 줌·폭력·방해·약속 | 게임 코드가 계기를 바로 만든다 | 0 |
| 필드 NPC와 대화 | 필드 대화 모델 응답 끝에 `[[관계:계기]]` 태그 1개까지 → 코드가 검사 | 0 (원래 부르는 호출) |
| 목격 | 같은 장면 사람에게 `위협`·`작은친절` 약하게 | 0 |

- 필드 대화 모델은 **본편 모델과 별개 호출**이라 본편 품질에 영향이 없다. 이미 대화마다 부르므로 계기 태그 한 줄은 거의 공짜다.
- 기존 필드 브랜치의 `favor ±1` 태그를 이 계기 태그로 바꾼다.

### 안 A. 모델 없음 (필드만)

- **무엇**: 초기값 표 + 필드 안 변화만. 본편 이야기는 관계에 반영하지 않는다.
- **타이밍**: 해당 없음.
- **장점**: 비용 0, 지연 0, 오판 0, 구현이 가장 쉽다. 본편 품질 영향 0.
- **단점**: 본편에서 쟈알디와 크게 싸워도 필드의 쟈알디는 모른다. 본편과 필드가 따로 논다.
- **어울리는 경우**: 1단계 구현, 또는 보조 모델이 없는 사용자.

### 안 B. 본편 모델이 태그를 씀 (매 턴, 변화 때만)

- **무엇**: 카드 지침에 「관계가 바뀐 턴에만 `[♥|인물|계기|이유]`」를 넣는다. `onOutput`에서 정규식으로 읽는다.
- **타이밍**: 매 응답 직후, 같은 응답 안.
- **비용**: 추가 호출 0. 출력 토큰 소폭 증가. 카드 지침 약 400자 증가(매 요청).
- **장점**: 가장 빠르고 정확한 시점. 다시 굴리기와 저절로 맞음(태그가 그 응답 안에 있음).
- **단점** (사용자 우려, 타당함):
  - 본편 모델이 이미 태그 4~5종을 쓰고 있다. 태그가 하나 더 늘면 상태창·요원 태그 누락이나 형식 깨짐이 늘 수 있다.
  - 관계를 판정하느라 본문에 쓸 주의가 줄어든다. 「관계 변화를 만들려고 사건을 일으키는」 쪽으로 이야기가 휠 수도 있다.
  - 모델·프리셋마다 지침을 따르는 정도가 달라서 품질이 들쭉날쭉하다.
- **판단**: **기본값으로 쓰지 않는다.** 메뉴에 「실험: 본편 모델이 직접 기록」으로만 남기고, 켜기 전에 정확도·누락률을 시험한다(10장).

### 안 C. 보조 모델이 매 턴 읽음 (리수폿 Writer 방식)

- **무엇**: 본편 응답이 저장된 뒤(`onOutput`) 뒤에서 보조 모델을 부른다. 입력은 방금 응답(과 직전 사용자 입력), 출력은 계기 JSON.
- **타이밍**: 매 응답 직후, 백그라운드. 다음 입력을 막지 않는다.
- **비용**: 매 턴 1회. 입력 약 2~4천 토큰(응답 + 등장인물 짧은 시트 + 현재 관계 + 규칙), 출력 100~300 토큰.
- **장점**: 본편 모델에 영향 0. 시점이 정확하다(한 턴씩). 판정이 전용 지침이라 품질이 좋다.
- **단점**: 매 턴 비용과 호출 수. 무료·저가 보조 모델은 속도 제한에 걸릴 수 있다. 괴담톡 자동과 겹치면 호출이 둘이 된다(→ 안 E로 묶음).
- **어울리는 경우**: 보조 모델이 싸고 빠른 사용자(예: 가벼운 모델).

### 안 D. 보조 모델이 몰아서 읽음 (추천 기본)

- **무엇**: 마지막으로 읽은 곳(`scan.lastIndex`) 이후 쌓인 본편 메시지를 한 번에 읽고, 구간 안의 관계 사건을 메시지 번호와 함께 받는다.
- **타이밍** (메뉴에서 고름, 여러 개 동시 가능):
  1. **N턴마다**: 읽지 않은 응답이 N개(기본 10) 쌓이면 `onOutput` 뒤에서 자동.
  2. **필드(게임)를 열 때**: 읽지 않은 응답이 M개(기본 3) 이상이면 뒤에서. 게임은 저장값으로 바로 시작하고 결과가 오면 갱신(「관계 갱신 중…」 작은 표시).
  3. **수동**: 메뉴의 「지금 관계 갱신」.
- **비용**: N턴에 1회. 입력은 구간 길이에 비례(10턴이면 약 1~2만 토큰), 출력 수백 토큰.
- **장점**: 본편 영향 0. 호출 수가 적다. 구간을 넓게 보니 「며칠에 걸친 화해」 같은 흐름을 잡기 쉽다.
- **단점**:
  - 반영이 늦다(최대 N턴).
  - 구간이 길면 모델이 사건을 빠뜨리거나 메시지 번호를 틀린다 → 한 번에 최대 20턴, 넘으면 나눠 부른다.
  - 다시 굴리기를 한 메시지가 이미 읽은 구간 안이면: 그 메시지의 옛 사건은 자동으로 빠지지만(anchor) 새 응답은 다음 몰아 읽기 때까지 안 읽힌다 → `scan`에 「다시 읽을 메시지 목록」을 두고 다음 호출에 포함(8-1).
- **판단**: 기본으로 추천. 「N턴마다 + 게임 열 때」를 기본으로 켠다.

### 안 E. 기존 자동 호출에 얹기 (괴담톡·괴담넷)

- **무엇**: 괴담톡·괴담넷 자동이 켜져 있으면 이미 매 턴 보조 모델을 부른다(`Joint`로 둘을 한 번에). 여기에 세 번째 작업 `relation`을 넣어 한 응답에서 같이 받는다.
- **타이밍**: 괴담톡·괴담넷 자동과 같은 순간(매 응답 뒤).
- **비용**: 추가 호출 0. 입력 토큰은 관계 규칙·관계 현황만큼 늘어난다(약 1~2천). 출력 수백 토큰.
- **장점**: 호출 수가 늘지 않는다. 본편 영향 0. 시점 정확.
- **단점**:
  - 그 기능을 켠 사용자에게만 해당한다.
  - 한 응답에 세 작업이 묶이면 서로 섞이거나 한쪽 품질이 떨어질 수 있다(괴담넷이 이미 「다른 작업 정보로 추론 금지」 규칙을 둔 이유). → 관계 작업 결과는 따로 검사하고, 실패하면 그 턴은 버리고 다음 몰아 읽기(안 D)에 맡긴다.
  - `Joint` 구조를 둘에서 셋으로 넓히는 코드 수정이 필요하다(`JointKind`, `INSTRUCTION`, `combinedPrompts`).
- **판단**: 괴담톡·괴담넷 자동을 켠 사용자에게는 이걸 기본으로. 꺼져 있으면 안 D.

### 안 F. 하이브리드 (추천)

```
필드 안 행동·대화 ─────────────── 코드/필드 대화 태그 (항상)
본편 이야기 ─┬ 괴담톡·괴담넷 자동 켜짐 → 안 E (매 턴, 추가 호출 0)
             ├ 꺼짐 → 안 D (10턴마다 + 게임 열 때)
             ├ 「지금 관계 갱신」 버튼 → 안 D 즉시
             └ (실험) 본편 모델 직접 기록 → 안 B
보조 모델 없음/관계 끔 → 안 A
```

- 어느 길로 들어온 사건이든 **같은 장부, 같은 판정 엔진**을 거친다.
- 안 E로 이미 읽은 메시지는 `scan`에 표시되어 안 D가 다시 읽지 않는다.

### 3-7. 메인 모델 vs 보조 모델 (본편 몰아 읽기·매 턴 읽기에 쓸 모델)

| | 보조 모델(`aux`, Risu 보조 모델) | 메인 모델(`main`, 따로 호출) |
| --- | --- | --- |
| 본편 품질 영향 | 없음 | 없음 (본편 요청과 별개 호출) |
| 판정 품질 | 모델에 따라 다름. 가벼운 모델은 계기 오판·인용 실수 | 좋음 |
| 비용 | 낮음 | 높음 (같은 비싼 모델을 한 번 더) |
| 속도 제한 | 무료 모델은 걸리기 쉬움 | 메인 요금제 공유 |
| 기본값 | **보조** | 선택 |

- 「메인 모델 사용」은 **본편 응답에 태그를 쓰게 하는 것(안 B)과 다르다.** 같은 모델을 별도 요청으로 부르는 것이라 본편 품질과 무관하다. 사용자에게 이 차이를 메뉴 설명에 분명히 적는다.
- 괴담톡·괴담넷과 같은 모델 설정을 쓰면 `Joint`로 묶을 수 있다(모델이 다르면 묶지 않고 따로 부름. 지금 `onOutput`의 규칙과 같음).

| | A 없음 | B 본편 태그 | C 보조 매 턴 | D 보조 몰아 읽기 | E 자동 호출에 얹기 | F 하이브리드 |
| --- | --- | --- | --- | --- | --- | --- |
| 본편 이야기 반영 | ✕ | ○ | ○ | ○(늦게) | ○ | ○ |
| 본편 품질 영향 | 없음 | **있음** | 없음 | 없음 | 없음 | 없음(B 끄면) |
| 추가 모델 호출 | 0 | 0 | 매 턴 1 | N턴에 1 | 0 | 0~N턴에 1 |

## 4. 모델 동작 지침 (프롬프트 초안)

몰아 읽기(D)·매 턴(C)·얹기(E)가 같은 지침을 쓴다. 영어로 쓰는 이유: 기존 괴담넷·괴담톡 지침과 같은 언어(모델 준수율). 출력 문장(reason)은 한국어.

### 4-1. 시스템 지침

```
# Relationship Ledger — Event Extraction

You read a span of a Korean roleplay and report only NEW, actually depicted events that change
how one named character personally feels about another (or about the user's character).
You never write story prose. You never compute scores; the program does.

## Direction
- Each event has `from` (the one whose feeling changes) and `to` (target). `to` is a supplied
  character name or "@user". Never record the user's own feelings (from = "@user" is forbidden).
- Record both directions only when both sides were actually affected.

## What counts
- Use ONLY the supplied cue names. Pick the single best cue per event.
- An event must be depicted in the supplied span, with a short verbatim quote (5–60 chars)
  copied exactly from the span. No quote, no event.
- Judge by THIS character's values in the supplied sheet. The same act can please one
  character and annoy another.

## What never counts
- Greetings, appearance, rank or title, routine duties, small talk.
- An offer or request that has not been answered yet.
- Events retold in summaries, flashbacks, [필드 막간] blocks, or system/status lines.
- Anything already listed in `already_recorded`.
- Relationship labels alone ("colleague", "boss") are not events.
- A polite refusal or boundary is not a wrong.

## Limits
- At most 6 events per span, at most 2 per pair. Prefer fewer, clearer events.
- If nothing qualifies, return {"events": []}. Empty is a normal answer.
- Never invent names. Use only names from `characters` or "@user".

## Output
Return exactly one JSON object, no fences:
{"events":[{"msg":<message number>,"from":"<name>","to":"<name or @user>","cue":"<cue>",
"quote":"<verbatim>","reason":"<한국어 한 줄, 40자 이내>"}],
 "persona":{"faction":"<A00..>|null","rank":"<직급>|null"}}
`persona` is filled only if the span states the user character's organization or rank
clearly; otherwise null.
```

### 4-2. 사용자 메시지(데이터) 구성

```json
{
  "cues": [{"name":"작은친절","meaning":"..."}, ...],
  "characters": [
    {"name":"쟈알디","aliases":["부장","쟈알디 부장"],"values":"거짓말 안 함, 동료 생존 최우선, 감정 표현 적음",
     "now_toward_user":"보통(호감 5)"}
  ],
  "already_recorded": [{"msg":118,"from":"스팡달","to":"@user","cue":"무례"}],
  "span": [
    {"msg":120,"role":"user","text":"..."},
    {"msg":121,"role":"assistant","text":"..."}
  ]
}
```

- `characters`: 구간 안에 이름·별명이 나온 인물만(코드가 별명 표로 찾음). 성격은 2~3줄 요약(미리 만든 표 `temper`의 근거 문장).
- `span`: 상태창·상황판 태그·[필드 막간]·시스템 블록은 **코드가 지우고** 넣는다(4-1의 「막간 제외」를 코드로도 보장).
- 메시지 번호는 코드가 붙인 번호. 모델이 돌려준 `msg`로 `anchor`(chatId)를 찾는다.

### 4-3. 응답 검사 (코드)

1. JSON 파싱 실패 → 한 번 재시도(「JSON만」 짧은 재요청). 또 실패 → 그 구간 건너뛰고 「관계 갱신 실패」 기록, `scan`은 옮기지 않음.
2. 사건마다: `from`·`to`가 명단(별명 포함)에 있나 / `from ≠ @user` / `cue`가 표에 있나 / `msg`가 구간 안인가 / `quote`가 그 메시지 원문에 실제로 있나(공백·따옴표 정규화 후 부분 문자열) / 같은 쌍 2개 이하.
3. 하나라도 어긋난 사건은 **그 사건만** 버린다(리수폿과 달리 전체를 버리지 않음). 버린 이유는 기록 화면에 남김.
4. 통과한 사건 → 판정 엔진(2-6) → 장부 저장.
5. `persona`는 상태창 「신분」 칸이 없을 때만 참고값으로 쓴다(6장).

### 4-4. 필드 대화 태그 지침 (필드 대화 모델에 추가)

```
At the very end, you may add ONE tag if this exchange clearly changed how you feel about the visitor:
[[관계:<cue>]]  (cue from: 작은친절, 도움, 선물, 비밀공유, 실망, 무례, 위협)
Most exchanges add no tag. Never add a tag for greetings or small talk.
```

- 필드 대화 쪽은 계기 7개로 줄인다(큰 사건은 행동으로만 생김).

## 5. 본편에 반영하기 (읽는 쪽)

관계값을 **본편 모델에 알릴지**는 별도 선택이다. 알리지 않아도 필드 대사·필드 대화에는 쓰인다.

### 5-1. 선택지

| 방식 | 내용 | 본편 영향 | 기본 |
| --- | --- | --- | --- |
| 끔 | 본편에는 아무것도 안 넣음 | 없음 | |
| 장면 인물만 (추천) | 이번 요청에 이름이 나온 인물 + 상태창 동행 칸 인물, 보통이 아닌 관계만, 최대 5명 | 작음 | **켬** |
| 변화 알림만 | 지난 요청 이후 단계가 바뀐 관계만 한 줄씩 | 아주 작음 | |

### 5-2. 블록 모양 (`beforeRequest`에서 마지막 사용자 메시지 앞, 상태창 블록과 같은 자리)

```
[Relationship notes]
- 쟈알디 → {{user}}: 친근 (최근: 약속을 지켜 믿음이 늘었다). 말투·직급 관계는 그대로, 조금 더 챙긴다.
- 스팡달 → {{user}}: 불편 (최근: 무례한 말에 상처받았다). 필요한 말만 한다.
These are background tendencies, not events. Do not mention numbers. Do not force a scene about them.
```

- 숫자는 넣지 않는다(모델이 「호감도가 올랐다」 같은 메타 문장을 쓰는 것을 막음).
- 문장은 코드 템플릿(단계 → 문장, 최근 사건 reason 하나). 모델 호출 없음.
- 기존 `withStatusBlock`·`withVisit` 순서 뒤에 붙인다. 크기 상한 600자.
- 「캐릭터로 플레이」면 `{{user}}` 대신 그 요원 이름 기준으로 계산한다(`playerAgent`).

## 6. 유저 신분(소속·직급)

이미 정한 것: **상태창에 출력.**

### 6-1. 카드 지침 수정안 (🏷️Tag `## Status`)

```
[▣|YYYY.MM.DD|HH:MM AM/PM|weather|temperature|location|anomaly|companions|deployed|identity]
- Identity = {{user}}'s current organization and rank in Korean, as `조직/직급`
  (e.g. `관리국/신입`, `가짜 관리국/대리`, `백일몽/사원`, `프리랜서/5급`, `민간인/-`).
  Keep it unchanged unless the story actually changes it (promotion, transfer, defection).
```

- 파서(`status.ts`): 10번째 칸이 있으면 `identity`로 읽는다. 없으면 옛 8칸 그대로(깨지지 않음).
- 플러그인이 `조직` → 코드(A00…), `직급` → 사다리 숫자로 바꾼다(`docs/필드_대사_설계_결정.md` 사다리). 모르는 직급은 null → 그 조직 신입으로.
- 화면의 상태창 그림에는 이 칸을 그리지 않는다(동행·투입 칸과 같은 처리).
- **본편 모델에 칸 하나가 느는 것**이지만 「매 턴 관계 판정」과 달리 거의 안 바뀌는 값을 베끼는 일이라 부담이 작다. 그래도 정확도를 시험한다(10장).
- 보조: 상태창에 없으면 몰아 읽기 응답의 `persona` → 그것도 없으면 시작 시 고른 세력 코드 + 신입.

### 7-2. 관계 화면 (요원 화면 `src/ui/agents.ts`에 탭 추가)

```
┌ 관계 ───────────────────────── [지금 갱신] ┐
│ 나를 보는 시선 │ 인물끼리 │ 기록           │
├────────────────────────────────────────────┤
│ 쟈알디   친근 ■■■■■■□  믿음 ■■■□□  📌      │
│   최근: 약속을 지켰다 (#121) 「…」          │
│ 스팡달   불편 ■■□□□□□  믿음 ■□□□□          │
│   최근: 무례한 말 (#118) 「…」              │
│ …                                          │
└────────────────────────────────────────────┘
```

- **나를 보는 시선**: 인물별 단계 막대(숫자는 길게 누르면), 최근 사건 1개(메시지 번호 누르면 그 메시지로 이동), 📌 고정.
- **인물끼리**: 초기값 표 + 바뀐 쌍만 목록(필터: 바뀐 것만 / 전체).
- **기록**: 장부 전체. 출처 아이콘(필드·필드대화·본편·수동), 인용, 판정 결과. 항목마다 **[취소]**(그 사건만 무효, 사건에 `void: true`), **[되살리기]**.
- **직접 수정**: 인물 누르기 → 단계 선택 + 이유 입력 → `manual` 사건으로 저장(리수폿처럼 이유 필수). 고정하면 자동 변화가 쌓여도 값이 안 변한다.
- **갱신 상태**: 「관계 갱신 중…」, 「마지막 갱신: 121번 메시지까지」, 실패 시 「다시 시도」.
- **초기화**: 이 채팅의 관계 기록 지우기(확인 두 번).

### 7-3. 게임 안 표시

- E 대화칸 이름표 옆에 단계 아이콘(♡ 색), 변화가 생기면 머리 위 ↑↓ 작은 표시(기존 설계 6-2 「표시는 단어 한 줄」 유지).
- 「관계 갱신 중」은 화면 구석 작은 점 세 개.

## 8. 실제 개발 시 필요한 것과 예상 문제

### 8-1. 다시 굴리기·스와이프·삭제

- 사건은 `anchor`(chatId)로 살아 있음을 판단 → 응답이 바뀌면 옛 사건 자동 제외. **값이 저절로 맞다.**
- 새 응답을 다시 읽어야 하는 문제: `onOutput`이 오면 그 메시지가 「이미 읽은 구간」 안인지 보고, 안이면 `scan.reread`에 넣는다. 다음 호출(D든 E든)에 함께 넣는다.
- Risu 스와이프로 옛 응답으로 돌아가면 chatId가 옛 것으로 돌아오는지 **실제로 확인해야 한다**(미검증). 돌아온다면 옛 사건이 되살아난다(원하는 동작).

### 8-2. 채팅 복제·분기

- 장부가 `chat.scriptstate`에 있어 복제하면 같이 따라간다. 분기 뒤 각자 쌓인다. 기존 필드 저장과 같은 성질.

### 8-3. 긴 채팅·로그 잘림

- Risu가 오래된 메시지를 요청에서 빼도 **채팅에는 남아 있으므로** anchor 판단은 채팅 전체로 한다.
- 사용자가 메시지를 지우거나 요약 기능으로 오래된 메시지가 사라지면 그 사건이 빠진다 → 2-6의 「접기」로 오래된 사건은 미리 합쳐 둔다(최근 200개 메시지 밖).

### 8-4. 이름·별명

- 본편은 「부장」, 「쟈알디 부장님」, 영어 이름 등으로 부른다. 별명 표가 필요하다: 위키 정보칸 + 폰 연락처(`phone.ts`의 `english`, `terms`) + 사용자가 추가한 인물.
- 별명이 겹치면(「부장」은 여러 조직에 있음) 그 구간에 나온 조직을 보고 좁히고, 그래도 모르면 모델에게 넘기지 않는다.
- 위키에 없는 인물(사용자가 만든 NPC): 첫 등장 시 장부에 이름 그대로 저장, 초기값 0. 메뉴에서 합치기(같은 사람) 기능.

### 8-5. 필드 막간과의 이중 반영

- 필드에서 한 일은 이미 필드 사건으로 관계에 반영되고, `[필드 막간]`으로 본편 요청에 들어간다. 몰아 읽기가 막간을 다시 읽으면 두 번 오른다.
- 대응: 몰아 읽기 입력에서 막간 블록을 **코드가 빼고**, 지침에도 막간 제외를 적는다. 본편 응답이 필드 일을 다시 서술한 부분은 `already_recorded`에 필드 사건 목록을 넣어 막는다.

### 8-6. 기존 필드 브랜치 `Relations`(−3~+3)와 합치기

- 필드 브랜치는 브라우저 저장(`RelationStore`)에 favor −3~+3, 대화 기록, memo를 둔다. 새 장부는 채팅 저장이다.
- 옮기는 법: favor × 15 → 호감 초기 보정 `manual` 사건 하나(「옛 필드 호감 옮김」). 대화 기록·memo는 필드 쪽에 그대로 둔다.
- **이 일은 필드 브랜치 작업과 겹친다 → 구현 시작 전에 사용자 확인.**

### 8-7. 「캐릭터로 플레이」

- 유저가 특정 요원이면 `to = '@user'` 대신 그 요원 이름으로 계산해야 하나? → **아니다.** 장부는 언제나 `@user`(지금 플레이어)로 쌓되, 초기값을 `pairs["X>그 요원"]`에서 가져온다. 요원을 바꾸면 그 요원 기준으로 다시 계산(장부에 `as: 요원id`를 남김).

### 8-8. 페르소나 바꾸기

- 같은 채팅에서 RisuAI 페르소나를 바꾸면 다른 사람인가? → 장부 사건에 `persona` 이름을 남기고, 메뉴에 「페르소나별로 따로 / 같이」 선택(기본 같이). 드문 경우라 1단계에서는 같이.

### 8-9. 비용·속도 제한·동시 호출

- 몰아 읽기 입력 상한: 20턴 또는 2만 자. 넘으면 앞에서부터 나눠 여러 번.
- 동시 호출 방지: 관계 작업은 하나씩(큐). 괴담톡·괴담넷이 진행 중이면 기다렸다가 `Joint`로 묶거나 뒤에.
- 실패가 3번 연속이면 자동 읽기를 잠시 멈추고 메뉴에 알림.

### 8-10. 모델 오판

- 대표 오판: 인사에 점수 주기, 같은 사건 두 번, 남의 감정을 거꾸로(방향 착오), 위키에 없는 성격으로 판정.
- 대응: 인용 검사, 하루 상한, 체감, 사건 2개/쌍, 기록 화면에서 한 번에 취소. 정확도는 시험 세트로 잰다(10장).

### 8-11. 미성년·성인 표현

- 콘쥬스 등 미성년 인물: 최고 단계도 「믿고 따름·아낌」으로만 표현(문장 템플릿을 인물 속성 `minor`로 분기). 연애 계기는 표에 없다.
- 관계 기능 전체에 연애·성적 축을 두지 않는다(리수폿의 성인용 수치는 가져오지 않음).

### 8-12. 저장 크기

- 사건 하나 약 200자 × 600건 = 약 12만 자. 채팅 변수로는 크다 → 인용은 60자로 자르고, 접기 기준을 400건으로 낮출 수 있다. 실제 크기를 재고 정한다.

### 8-13. 옛 채팅 소급

- 기능을 처음 켠 긴 채팅: 「처음부터 읽기」 버튼(최근 50턴만, 비용 안내 후). 기본은 지금부터.

### 8-14. 카드 업데이트와 버전

- 상태창 「신분」 칸은 카드 수정 → `minPlugin` 올림. 관계 기능 자체는 카드 수정 없이 플러그인만으로 된다(안 B를 켤 때만 카드 지침 추가).

## 9. 대사 선택 알고리즘 (필드)

```
speaker S, 플레이어 P, 통로 ch(bark|talk), 진영 side(ally|enemy), 시간 t, 상황 sit
1. 상황 bark (투입·부상·경보 등) 조건이 맞으면 일정 확률로 situation[sit]
2. 혼잣말 확률(예: bark의 30%)이면 time[t]
3. P가 다른 인물(캐릭터로 플레이)이면:
     special[P.name] 있으면 그 칸
     아니면 관계칸 = hostile(호감≤−11) | close(호감≥41) | 직급 비교(boss/peer/junior) | outsider(다른 조직)

6. {호칭} 채우기: address[up|peer|down|outsider] (같은 조직 비교 결과 기준)
```

- 데이터: `game-src/dialogue/characters/*.json`, `npc/*.json`. 이 대화에서 작성 완료(검사 통과).

## 11. 만드는 순서 (추천)

1. **바닥**: `relation/engine.ts`(fieldrel 이전), 장부 저장(`goeiRelV1`), 판정 골든 시험. 초기값 표 `relations-base.json` 작성·검수.
2. **안 A**: 필드 행동·필드 대화 태그 → 장부. 대사 선택(9장)에 호감 반영. *(필드 브랜치와 합칠 때, 사용자 확인 후)*
3. **관계 화면·설정** 1차(목록·기록·직접 수정·끔/켬).
4. **안 D** 몰아 읽기(보조 모델) + 지침 + 검사 + 재읽기 목록. 시험 세트로 정확도 측정.
5. **본편 알리기**(5장) 장면 인물만.
6. **상태창 신분 칸**(카드 수정, `minPlugin`).
7. **안 E** `Joint` 세 작업으로 확장.
8. (선택) 안 C 매 턴, 안 B 실험.

## 12. 사용자가 정할 것

1. 추천안 F(하이브리드)로 갈지, 단순하게 A → D만 할지.
2. 호감 범위: −100~100(기존 코드) 그대로인가.
3. 신뢰 축을 둘지(호감 하나만 둘지).
4. 본편에 관계를 알릴지(기본 「장면 인물만」).
5. 몰아 읽기 기본 간격(10턴).
6. 인물끼리 관계(NPC↔NPC)도 본편에서 읽을지, 유저 대상만 읽을지. (유저 대상만이면 비용·오판이 크게 준다. **추천: 1단계는 유저 대상만**, 인물끼리는 초기값 표 고정.)
7. 시간 감쇠 기본 끔이 맞는지.
8. 필드 브랜치 `Relations` 이전 시점(필드 작업과 겹침).
